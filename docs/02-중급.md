## 1부: 컨텍스트 적극 관리 (가장 쉬운 / 큰 효과)

> compose.yaml 한두 줄로 가장 큰 효과를 낼 수 있는 영역. AGENTS.md 가 *수동적* 으로 자동 생성되는 게 입문이라면, 중급 1부는 그것을 *적극적으로 조작* — prefix 를 작업 중 동적으로 바꾸고, 도구 결과를 의도적으로 압축·제거하고, 컨텍스트 예산을 직접 조절.

## 1. 컨텍스트 관리

[입문 §6 AGENTS.md](01-입문.md#6-agents-md--자동-생성-흐름) 에서 본 압축 정책 (*"instructions / rules 본문은 압축 안 됨, context 의 path 참조는 압축됨"*) 은 *수동적*. 중급에서는 **적극적 관리** — prefix 를 작업 도중에 바꾸고, 도구 결과를 의도적으로 압축·제거하고, 컨텍스트 예산을 직접 조절.

### 1.1 Prefix 동적 조정

`compose.yaml`의 `prefix:` 리스트는 *세션 시작 시 한 번* 적용. 하지만 작업 도중에 *맥락이 바뀌면* 다른 md를 prefix로 박고 싶을 때가 있음:

- 백엔드 작업 중 → 갑자기 프론트엔드 영역 진입 → 다른 Persona 필요
- DB 마이그레이션 시작 → 데이터 명세서를 prefix에 강제 주입

**해결**: `harness reload --prefix-add know-how/FRONTEND.md` 같은 명령으로 *세션 중에도* prefix 갱신. session_start이 아닌 임의 시점에 resolved.md 재생성 + LLM에 *시스템 메시지로 알림*.

### 1.2 도구 결과의 의도적 압축·제거

큰 grep·Read 결과를 받으면 LLM 컨텍스트가 폭발. 압축 정책을 그냥 두면 *부분만 남고 일부 잃음*. 적극적 관리:

- **summary-then-discard**: sub-agent로 큰 파일 요약 받기 → 원본은 컨텍스트에 안 들임
- **explicit eviction**: `harness ctx evict <tool-call-id>` — 특정 도구 호출 결과를 즉시 제거
- **chunked reading**: 한 번에 큰 파일 안 읽고 part별로

### 1.3 컨텍스트 예산 추적

LLM 컨텍스트 윈도우는 한정. 세션이 길어지면 *절대 잊으면 안 되는 prefix* 도 위험. `harness ctx budget` 이 현재 예산 사용률을 **cognition entry 별** 로 분리해 보여준다 — 어느 entry 가 토큰을 잡아먹는지 한눈에:

```
Context Budget
──────────────────────────────────────────────────────
[cognition.prefix]              5,000 tokens   [▮▮▮ 12%]   ← 본문 직접 (시스템 안내 / 외부 검증 / Hard Rules)
  agents_md                     3,100
  backend_persona               1,100
  rule_no_destructive_db          800           (manifest role: hard_rule → ## Hard Rules 그룹)
[cognition.context.required]    2,800 tokens   [▮▮ 7%]
  project_readme                2,800
[cognition.context.triggered]     600 tokens   [▮ 1%]      ← 매칭된 것만 합성
  api_spec                        600
[cognition.context.suggested]   (lazy — 합성 X)
[recent tool results]          12,300 tokens   [▮▮▮▮▮▮▮▮▮▮▮▮ 31%]
[compressed history]            6,500 tokens   [▮▮▮▮▮▮ 16%]
──────────────────────────────────────────────────────
Total:                         27,200 / 200,000 (14% used)
```

이 표가 **컨텍스트 적극 관리의 첫 출발점** — 무거운 `cognition.prefix` artifact 한 개만 줄여도 전체 prefix 가 가벼워진다. `cognition.context.suggested` 는 lazy 라 합성 안 됨 — 토큰 0 (필요 시점에만 도구로 로드). `triggered` 는 매칭된 것만 합성되므로 평소엔 가벼움.

### 1.4 압축 정책 적극 활용 — Hard Rules에 직접 명시

입문 4.3에서 본 *압축 정책*을 적극 활용하는 패턴:
- **잊으면 안 되는 룰**은 AGENTS.md Hard Rules에 *직접 본문* (path 참조 X) — 세션 끝까지 살아남음
- **자주 참조하는 path**는 Suggested Context 로 lazy 등록 — 필요할 때 LLM 이 도구로 읽음
- **단발성 결정**은 `runtime/shared/`로 promote → 다음 세션 prefix

### 1.5 다음 — 포커스 적극 활용

## 2. Persona 적극 활용

기본 Persona가 *"이 에이전트는 누구인가"* 한 줄이라면, 적극 활용은 *"task에 따라 다른 persona가 동작한다"* 의 다단계 시스템.

### 2.1 여러 persona 두기

`know-how/personas/` 폴더에 역할별 md 작성:

```
know-how/personas/
├── backend-dev.md      # 백엔드 개발자
├── frontend-dev.md     # 프론트엔드 개발자
├── test-writer.md      # 테스트 작성자
└── doc-editor.md       # 문서 정리 보조
```

각 파일은 입문 6.3의 3 요소(역할·책임·다루지 않는 영역) 형식. compose.yaml이 *어떤 persona를 활성화할지*를 결정.

### 2.2 Task 라우팅 — `compose.yaml` 또는 trigger

```yaml
# compose.yaml
persona:
  active: backend-dev          # 기본 활성

  # 또는 trigger로 자동 스위칭:
  trigger:
    - { match_path: "**/*.tsx", persona: frontend-dev }
    - { match_path: "tests/**", persona: test-writer }
    - { match_path: "docs/**",  persona: doc-editor }
```

`pre_tool_use` hook이 file_path를 trigger와 매칭 → 해당 persona를 prefix에 *동적으로 합성* (1.1 절의 prefix 동적 조정 메커니즘).

### 2.3 Multi-persona orchestration

복합 작업(예: feature 추가)에 여러 persona를 *순차*로 호출:

```yaml
ralph:
  stages:
    - persona: backend-dev
      task: ./know-how/stages/01-api.md
    - persona: test-writer
      task: ./know-how/stages/02-tests.md
    - persona: doc-editor
      task: ./know-how/stages/03-docs.md
```

ralph 가 stage 별 persona 를 자동 스위칭. 각 stage 는 깨끗한 컨텍스트 (전 stage 의 결과만 받음) + 해당 persona prefix.

> 여기까지는 *한 provider 안에서 persona 만 스위칭* 하는 패턴. **persona 별로 다른 provider** 까지 분리하는 활용 (예: backend-dev = claude / doc-editor = codex) 은 [§7.4 Persona × Provider 분리](#74-persona--provider-분리--역할-별-다른-모델) 참고.

### 2.4 Subagent에 persona 주입

4장의 Subagent 위임 시, sub-agent에 *명시적으로 persona 지정*:

```
Task("test-writer persona로 src/auth/* 테스트 작성. 결과: 테스트 파일 path 목록만")
```

부모는 `backend-dev`, sub-agent는 `test-writer` — *역할 분담*이 진짜로 일어남.

### 2.5 Persona vs Hook — 어디까지 강제할까

Persona는 *prompt 권고*에 가깝다 (LLM이 무시하려면 무시 가능). 진짜 *차단*은 hook의 일. 즉:
- Persona: "이 영역만 다룬다" *(부드러운 권고)*
- Conditional Required Context + 가드레일: "이 영역 외엔 Edit 차단" *(물리적 차단)*

둘을 같이 쓰면 *권고+차단*이 겹쳐 강력. Persona만으로 안전을 기대하지 말고, *적어도 가드레일*과 함께.

## 3. 세션 횡단 컨텍스트

매 세션은 깨끗한 컨텍스트로 시작한다. 입문에서는 그게 *안전 자체*였다 (어제의 잘못된 추측이 오늘로 안 따라옴). 하지만 *건강한 결정·검증된 패턴*도 같이 사라지는 게 단점. 중급은 **선별적으로 보존**하는 메커니즘.

### 3.1 무엇을 세션 간 공유할 만한가

| 공유 가치 높음 | 공유 가치 낮음 |
|---|---|
| 검증된 결정 (예: "auth는 JWT, refresh token 7일") | 임시 추측·실험 |
| 자주 마주치는 함정 + 해결 (예: "X 라이브러리는 ESM에서 Y 워크어라운드") | 단발성 디버깅 로그 |
| 도메인 용어 정의·약어 | 진행 중인 task의 부분 결과 |
| 사용자 선호·스타일 (예: "함수형 우선, 간결한 주석") | 한 번 쓰고 버린 코드 |

### 3.2 어떻게 보존하나 — `runtime/shared/`

`<project>/.harness/runtime/sessions/<id>/`는 세션별 격리. 그 옆에 **`runtime/shared/`** 같은 store를 두고 *세션 횡단으로 누적*시킨다.

```
<project>/.harness/runtime/
├── sessions/<id>/         # 세션별 격리 (입문에서 본 것)
└── shared/                # 세션 횡단 공유 store (NEW)
    ├── decisions.md       # 검증된 결정 누적
    ├── pitfalls.md        # 함정·해결 패턴
    └── conventions.md     # 도메인 용어·약어
```

`session_start` hook이 매 세션 시작 시 `runtime/shared/*.md`를 *AGENTS.md prefix에 합성*. 결과: LLM이 매 세션 *과거 결정·함정*을 prefix로 받음.

### 3.3 어떻게 갱신되나 — 명시적 promote

자동 추출(LLM이 알아서 보존)은 **위험** — 잘못된 추측까지 보존될 수 있음. 명시적 명령으로:

```bash
harness shared add decisions "JWT 토큰은 access 15분 / refresh 7일로 결정"
harness shared add pitfalls "ESM 환경에서 X 라이브러리는 named export만 가능"
```

또는 prompt에 마커:

```
@harness remember "이 결정은 다음 세션에도 유지"

JWT는 ...
```

`user_prompt_submit` hook이 마커 감지 → `runtime/shared/`에 append.

### 3.4 압축과의 관계

세션 내 컨텍스트는 압축됨 (1장에서 자세히). 하지만 `runtime/shared/`의 본문이 prefix로 합성되면 **압축되지 않음** — 세션 끝까지 LLM이 보고 있음. 절대 잊으면 안 되는 결정·패턴은 여기.

### 3.5 두 provider 간 공유 — claude ↔ codex

하네스가 관리하는 공유 풀 (`runtime/shared/`, `traces/`, `decisions.jsonl` 등) 은 **provider 무관**. 한 프로젝트에서 claude 세션과 codex 세션이 같은 풀을 함께 쓴다.

| 자산 | provider 공유 |
|---|---|
| `runtime/AGENTS.resolved.md` — LLM prefix 본문 | ✓ 같은 파일을 양쪽 adapter 가 각자 방식으로 주입 |
| `runtime/shared/` — 세션 횡단 컨텍스트 | ✓ 둘 다 같은 풀에서 읽고 씀 |
| `runtime/traces/<session-id>.jsonl` — 도구 호출 trace | ✓ 형식 통일 — codex 세션의 trace 를 claude 세션이 읽기 가능 |
| `runtime/sessions/<session-id>/decisions.jsonl` | ✓ 통일 형식 |
| provider native memory (`~/.claude/memory`, `~/.codex/...`) | ✗ provider 별 영역 — 공유 안 됨 |

**운영 패턴 예**: claude 로 코드 작성 → codex 로 디버그 → 둘 다 같은 `runtime/shared/` 풀에서 같은 결정·노하우 공유. 또는 claude 가 만든 trace 데이터를 codex 가 분석.

> **결정**: hard rules 나 핵심 노하우는 provider native memory 가 아닌 `runtime/shared/` 또는 know-how 의 instructions artifact 에 두기. 그래야 provider 무관하게 보존되고, 한 provider 로 만든 결정을 다른 provider 가 그대로 받음.

## 4. Subagent 위임

한 에이전트가 모든 작업을 직접 하면 컨텍스트가 과하게 쌓이고 *산만*해진다. **Task 도구로 sub-agent를 호출해 작업을 위임**하면 (1) 부모 에이전트의 컨텍스트가 가벼워지고 (2) 위임된 작업은 sub-agent의 깨끗한 컨텍스트에서 실행 — 둘 다 품질·속도 모두 이득.

### 4.1 언제 위임하나

- **탐색·검색**: 코드베이스 큰 영역 grep/find — 결과를 다 부모에게 가져오면 컨텍스트 폭발
- **반복 작업**: 같은 패턴의 30개 파일 변환 — 부모가 다 하면 cognitive guard에 걸리거나 doom loop
- **독립적 sub-task**: "테스트 작성" / "타입 정의 추가" / "마이그레이션 스크립트 작성" — 결과만 받으면 됨
- **요약 생성**: 큰 로그·문서를 요약해 부모는 핵심만

부모의 컨텍스트는 *총괄·결정*에, sub-agent는 *수행*에 집중.

### 4.2 Subagent에 무엇을 넘기나

| 항목 | 내용 |
|---|---|
| 명확한 task | "src/auth/ 안 모든 .ts 파일에서 deprecated `authV1()` 호출을 찾아 목록만 반환" |
| 결과 형태 명시 | "JSON array of {file, line, context}" — 부모가 받기 좋은 형태 |
| 범위 제한 | 만지지 말 것·읽지 말 것 명시 ([입문 §11 Persona](01-입문.md#11-persona--범위-제한) 의 *다루지 않는 영역* 과 같은 원리) |
| 필요한 컨텍스트만 | sub-agent가 따로 Read 할 path 안내 |

### 4.3 Subagent도 가드레일을 받음

입문에서 본 **모든 가드레일이 sub-agent에도 동일하게 작동**:
- Required Context 미읽음 → sub-agent가 Edit 시도 시 차단
- Cognitive guard → sub-agent의 큰 변경도 차단
- Stop validation → sub-agent의 응답 종료 직전에도 검증

즉 위임이 *방어를 우회하는 길이 아님*. Sub-agent도 같은 안전 망 안에서 일함.

### 4.4 좋은 위임 vs 나쁜 위임

| 좋은 위임 | 나쁜 위임 |
|---|---|
| "이 폴더 안 deprecated 호출 찾기" — *명확한 입출력* | "코드 정리해줘" — *모호한 task, 결과 형태 불명* |
| "테스트 작성 — 결과는 파일 path만 반환" | "테스트 작성하고 알아서 잘 해줘" |
| 한 번 호출 → 결과 받고 → 부모가 통합 | 같은 폴더에 10번 sub-agent 호출 → 부모가 정리 못함 |

### 4.5 다음 — Worktree 병렬

Subagent가 *한 세션 내 위임*이라면, Worktree는 *여러 작업을 동시에* 돌리는 방식. 같은 repo의 다른 branch에서 독립된 에이전트들이 병렬로 일함.

## 5. Worktree 병렬

git의 `worktree` 기능을 쓰면 한 repository를 여러 디렉토리에 *동시에 체크아웃* 가능. 각 디렉토리에서 독립된 claude 세션을 돌리면 **여러 작업이 진짜로 병렬 실행**된다 — feature A를 한 worktree에서, feature B를 다른 worktree에서.

### 5.1 왜 worktree가 필요한가

단일 repo에서 여러 작업을 *번갈아 가며* 하면 매번 git stash·checkout 비용. 또 LLM 입장에서 *한 세션이 여러 feature를 다루다*가 컨텍스트 혼선. Worktree는 그 둘을 동시에 해결:

- 각 worktree = 독립 폴더 + 독립 branch
- 각 worktree에서 별도 claude 세션 시작
- 각 세션은 자기 작업에만 집중 (컨텍스트 깨끗)

### 5.2 하네스와의 결합

각 worktree는 자기 `<worktree>/.harness/`를 가짐. 처음 worktree 생성 시 한 번만 `harness init` + `harness link claude`. 그 후엔 그 worktree에서 시작한 claude 세션이 자동으로 하네스 적용.

```bash
# 메인 repo에서
git worktree add ../my-project-feature-a feature/auth
git worktree add ../my-project-feature-b feature/billing

# 각 worktree에서
cd ../my-project-feature-a
harness init
harness link claude
claude    # 이 세션은 feature-a만

# 다른 터미널에서 동시에
cd ../my-project-feature-b
harness init
harness link claude
claude    # 이 세션은 feature-b만
```

### 5.3 Compose.yaml 공유 vs 분리

각 worktree가 *완전 독립된 compose.yaml*을 가질 수도, *공유*할 수도 있음:

| 전략 | 방법 | 사용 시나리오 |
|---|---|---|
| **완전 독립** | 각 worktree 가 자기 `.harness/compose.yaml` + `know-how/` | 작업 성격 다름 (예: feature 코드 vs docs) — 다른 가드레일 임계값 |
| **부분 공유** | 메인 worktree 의 `compose.yaml` 한 파일을 모든 worktree 가 참조 | 같은 정책을 모든 worktree 에 적용 |
| **Know-how 만 공유** | `know-how/` 폴더 자체를 공유 자산으로 | 정책은 worktree 별, 자산은 공유 |

### 5.4 cognitive guard와의 상호작용

`per_session` 메트릭은 *세션별*로 작동. Worktree마다 독립 세션이라 *각 worktree는 자기 세션 누적*만 카운트. 즉 두 worktree에서 합쳐 1500 line 변경해도 각 500/1000 limit에 안 걸림 — 각자 독립.

이게 **장점** (병렬 throughput ↑) 이자 **위험** (전체 변경 폭 통제력 ↓). 위험은 1부 컨텍스트 관리에서 본 압축 정책 + [고급](03-고급.md) 의 trade-off 에서 다시 다룸.

### 5.5 다음 — 자가 구동

위임·병렬은 사람이 매 응답에 개입하면서 *공간을* 나누는 것. 다음 5부 Ralph 는 사람 없이 task 만 주고 검증 통과까지 *자가 루프*.

## 5부: 자가 구동 (workflows)

> 1-4 부는 사람이 매 응답에 개입. 5부 Ralph 는 task 만 주고 검증 통과까지 사람 없이 자가 루프.

## 6. Ralph 무인 루프

지금까지 본 모든 강제력·가드레일은 *사람이 같이 있는 세션*을 가정. Ralph는 그걸 뒤집어 **사람 없이 task만 주고 떠나는** 모드. LLM이 task를 받아 → 작업 → verify → 통과까지 반복.

### 6.1 Ralph가 뭐고 언제 쓰나

이름 그대로 *루프*. 한 번에 끝나지 않을 큰 작업(예: 마이그레이션, 대규모 리팩토링)을 task 명세서로 적어두고 떠나면, ralph가 verify가 통과할 때까지 반복적으로 LLM을 호출. 가드레일은 그대로 동작 — `ask_human` 정책은 자동으로 `abort`로 fallback.

### 6.2 활성화

`compose.yaml` 의 `state.workflows` 에 ralph entry 추가:

```yaml
state:
  workflows:
    - id: ralph
      task: ./know-how/ralph-task.md   # 작업 명세 (필수)
      max_iterations: 20
      verify:
        commands:                       # 모두 exit 0 → loop 종료 (성공)
          - "pytest -x"
          - "tsc --noEmit"
      stuck_threshold: 3                # 같은 path 연속 수정 카운터
      on_stuck: ask_human               # ask_human | abort
```

### 6.3 검증 — verify 통과 = loop 종료

`verify.commands` 의 모든 shell command 가 exit 0 으로 끝나면 loop 종료 (성공). 하나라도 실패하면 직전 verify 출력을 다음 iteration prompt 에 포함시켜 LLM 이 수정하도록.

`verify.commands` 미지정 시 검증 단계 skip — 사용자가 invoker 호출만 `max_iterations` 까지 반복.

### 6.4 Stuck Detection — 같은 자리에서 멈춤

`stuck_threshold: 3` 초과 (verify 점수가 N회 같음 또는 변경 없음) → `on_stuck` 정책:
- **`ask_human`** (default): 사람에게 알림 (ralph 모드에선 자동 abort)
- **`abort`**: 즉시 종료

이건 [입문 §9 의 doom loop](01-입문.md#9-가드레일--켜고-끄기) 와 비슷한 의도지만 *루프 차원* 에서의 stuck 감지.

### 6.5 Invokers — Provider별 LLM 호출 매개체

Ralph는 LLM을 *비대화*로 호출해야 함. provider별로 그 방법이 다름:

| Invoker | 방식 |
|---|---|
| `manual.sh` (default, 안전) | 사람이 매 iteration mediation. 처음 써볼 때 권장 |
| `claude.sh` | `claude --print` 비대화 모드 (claude code 구독 활용) |

추가 provider 는 `standard/workflows/ralph/invokers/<name>.sh` 추가만 하면 됨.

### 6.6 다음 — 품질 (여러 시각)

Ralph 가 *한 모델로 사람 없이 루프* 였다면, 다음 6부는 *여러 모델의 조합* 으로 품질을 올림 — Multi-agent ensemble.

## 6부: 품질 — Multi-agent ensemble

> 한 모델의 한계를 넘어 여러 모델을 조합. 같은 task 를 동시에 풀거나 (parallel), 비평·반복 개선 (sequential).

## 7. Multi-agent ensemble

여러 LLM 모델·persona를 *동시 또는 순차*로 호출해 답변을 비교·통합하는 방식. 단일 모델로는 못 잡는 오류·놓친 관점을 보완.

### 7.1 언제 ensemble이 필요한가

- **중요 결정**: 아키텍처 선택, 보안 정책, 마이그레이션 계획 — 한 모델의 누락은 비싼 비용
- **검증이 어려운 답변**: 정성 답변(설계 리뷰, 코드 품질 평가) — 여러 시각이 합의해야 신뢰
- **사각지대 있는 모델**: 특정 도메인에서 약한 모델은 다른 모델로 보완

### 7.2 두 패턴 — 동시 vs 순차

| 패턴 | 동작 | 비용 |
|---|---|---|
| **동시 (parallel)** | 같은 prompt를 N 모델에 동시 보냄 → 답변 비교·합의 | N배 token |
| **순차 (sequential)** | 모델 A 답변 → 모델 B에게 *비평·보완* 요청 → 통합 | 약 2~3배 + 추가 라운드 |

동시는 *독립적 시각* 얻기, 순차는 *비평·반복 개선* — 다른 의도.

### 7.3 어떻게 호출하나 — invokers 확장

§6 Ralph invokers 패턴을 확장:

```
~/.harness/standard/workflows/ralph/invokers/
├── manual.sh
├── claude.sh           # 단일 모델
├── ensemble.sh         # 여러 invoker 호출 + 결과 합성 (NEW)
└── codex.sh            # 다른 provider
```

`ensemble.sh`는 두 개 이상의 invoker(claude+codex 등)를 호출하고 결과를 합성. compose.yaml에서 활성화:

```yaml
ralph:
  invoker: ensemble
  ensemble:
    invokers: [claude, codex]
    mode: parallel               # parallel | sequential
    aggregator: ./know-how/aggregate.sh   # 합성 스크립트
```

### 7.4 Persona × Provider 분리 — 역할 별 다른 모델

같은 ensemble 안에서 invoker 마다 **다른 persona + 다른 provider** 를 줄 수 있다. 예: 백엔드 코드는 claude / 문서 정리는 codex 가 각자 자기 역할로.

**두 활용 모드:**

| 모드 | yaml | 의미 |
|---|---|---|
| **stages (순차)** | `ralph.stages` 에 stage 별 `invoker` + `persona` 명시 | 다음 stage 가 이전 결과를 받음 — 파이프라인 |
| **ensemble (동시)** | `ralph.ensemble.invokers` 에 `{id, persona}` 리스트 | aggregator 가 결과 통합 — 한 task 에 여러 시각 |

stages 예 (순차):
```yaml
ralph:
  stages:
    - {persona: backend-dev, invoker: claude, task: ./know-how/stages/01-api.md}
    - {persona: doc-editor,  invoker: codex,  task: ./know-how/stages/02-docs.md}
  aggregator: ./know-how/aggregate.sh
```

ensemble 예 (동시):
```yaml
ralph:
  invoker: ensemble
  ensemble:
    invokers:
      - {id: claude, persona: backend-dev}
      - {id: codex,  persona: doc-editor}
    mode: parallel
    aggregator: ./know-how/aggregate.sh
```

**결과 추합 위치 — aggregator, not PostToolBatch.** `PostToolBatch` hook 은 *한 세션 안* 에서 도구 묶음 종료 시 metric 집계용 (입문 §10). 두 provider 세션의 결과 통합은 hook 영역 밖이고, **workflow 의 `aggregator` 스크립트** 가 담당:

```
[invoker A: claude / backend-dev]  →  stage_A.md
                                            ↘
[invoker B: codex  / doc-editor]   →  stage_B.md
                                            ↘
                                 aggregator.sh
                                 (두 결과 통합 → 최종 산출물)
                                            ↘
                                 runtime/shared/decisions.md (선택)
```

**provider native memory 가 공유 안 되니까** ([§3.5](#35-두-provider-간-공유--claude--codex)) — stage 간 전달할 결정·노하우는 native memory 가 아닌 `runtime/shared/` 에 둬야 다음 stage (다른 provider) 가 prefix 로 받을 수 있다. aggregator 가 통합 결과를 `runtime/shared/` 에 append 하는 패턴이 자연스러움.

### 7.5 LLM-as-judge로 품질 측정

Ensemble 답변 중 *어느 게 좋은지* 사람이 매번 판단할 수 없음. **LLM-as-judge**(§10)가 정성 점수 매김:

- 입력: prompt + 후보 답변 N개
- 출력: 각 답변 0~10 점수 + 짧은 평
- 활용: 점수 가장 높은 답변 채택, 또는 합성 시 가중치

### 7.6 비용 관리

Ensemble은 *N배 token*이라 매 prompt에 쓰면 비용 폭발. 트리거를 좁힘:

- **수동 활성**: 사용자가 prompt에 `@harness ensemble` 마커
- **자동 트리거**: 특정 path 매칭 시만 (예: `compose.yaml`·아키텍처 문서 변경 시)
- **stage 한정**: ralph stage chain의 특정 stage만 ensemble (검증 단계 등)

### 7.7 다음 — 측정·진화

여기까지 1~6 부가 *동작* 중심. 다음 7부는 그 동작을 측정·개선·진화시키는 도구들 — eval (회귀), 시각화, 패턴 분석, 진화 추적.

## 8. Eval (회귀 테스트)

코드를 고치다 보면 hook 동작이 미묘하게 깨질 수 있다. Eval은 우리 hook이 *예상대로 동작하는지*를 자동으로 검증하는 회귀 테스트 시스템.

### 8.1 케이스 포맷 — YAML로 hook 입출력 명세

각 케이스는 `setup` (임시 프로젝트 상태) + `input` (hook에 보낼 envelope) + `expect` (기대 출력)을 명시:

```yaml
id: required-deny
description: Required 미읽음 시 Edit 거부
type: hook_unit
hook: pre_tool_use
setup:
  init_harness: true
  compose_overrides:
    cognition:
      context:
        required:
          - {id: project_readme, src_path: README.md, label: "README"}
input:
  tool_name: Edit
  tool_input: { file_path: "src/foo.ts", ... }
expect:
  decision: self_correct
  reason_contains: "Required 미읽음"
```

### 8.2 기본 5 케이스

`~/.harness/standard/evals/cases/`:
- `required-deny` — Required 미읽음 시 Edit deny
- `required-allow-after-read` — Read 후엔 Edit 통과
- `required-hard-stop` — `on_deny: hard_stop` 시 turn 정지
- `cognitive-guard-per-call` — per-call 임계값 초과 시 deny
- `loop-detection` — 같은 path 연속 N회 시 deny

프로젝트별 추가 케이스는 `know-how/evals/cases/`.

### 8.3 실행 흐름

```
harness eval [<case-id>...]
    ↓
lib/eval/runner.py
    ├─ 임시 디렉토리에 mock harness 생성 (setup)
    ├─ hook 직접 호출 (claude 안 거침 — 빠르고 결정론적)
    ├─ exit code/stderr/stdout이 expect와 매칭되는지 검사
    └─ 결과를 runtime/eval-results/<ts>.json에 누적
```

### 8.4 Regression 감지

여러 시점의 결과를 비교해 *전엔 통과했던 케이스가 지금 실패하는지* 자동 감지. `harness viz eval`이 추세 + regression 알림.

## 9. 시각화 + Dashboard

세션이 끝난 뒤(또는 진행 중) 무엇이 일어났는지 한눈에 보는 도구. trace·decisions·timing을 입력으로 받아 mermaid·표·HTML을 생성.

### 9.1 6 viz 렌더러

| 명령 | 출력 | 답하는 질문 |
|---|---|---|
| `viz workflow [--live]` | mermaid 워크플로우 | "지금 어떤 흐름이 돌아가고 있나?" — compose.yaml hook 토글 동적 반영 (off는 disabled 스타일) |
| `viz subagents` | sequence diagram | "Task 도구로 어떤 sub-agent가 호출됐나?" |
| `viz bottleneck` | 표 (느린 도구 순) | "어디가 느린가?" |
| `viz eval` | 추세 + regression | "회귀 테스트 결과는?" |
| `viz improve` | 룰 기반 제안 카드 | "어떻게 개선할까?" |
| `viz prompts` | struggle score 분석 | "어떤 prompt가 잘 안 풀렸나?" |

### 9.2 출력 포맷

`--format` 옵션:
- `terminal` (default) — ASCII 표·텍스트
- `mermaid` — mermaid 코드만

## 10. Improve + LLM-as-judge

9장의 viz는 *현황*을 보여주고, 10장의 improve+judge는 한 발 더 나가 *어떻게 바꿀지*를 제안.

### 10.1 Improve — 룰 기반 제안

`harness improve`가 decisions·trace·eval-results를 종합 분석 → Python if-else 룰로 제안 카드 출력.

대표적 룰들:
- *Cognitive guard deny + bypass marker가 자주 같이 발동* → "임계값을 상향해도 안전" 제안
- *Loop detection이 자주 발동* → "consecutive_same_path 상향 검토"
- *특정 Required path가 자주 deny됨* → "AGENTS.md Hard Rules에 직접 인용 권장"
- *Eval regression 감지* → "최근 변경 검토 알림"

**의도적 제한**: *자동 적용*은 하지 않음. 제안만 노출, 적용은 사람이 결정 → 안전.

### 10.2 Prompt Struggle Score — "어떤 prompt가 잘 안 풀렸나"

매 prompt마다 점수 계산:

```
struggle = denies × 2 + retries × 3 + duration_s / 10 + bypass × 1
```

- `denies`: hook deny 횟수 → 가드레일에 자주 막힘
- `retries`: 같은 도구 호출 반복 → loop 신호
- `duration_s`: 응답까지 걸린 시간 → 복잡도
- `bypass`: bypass marker 사용 → 정상 정책으론 안 풀림

점수 높은 prompt를 dashboard Prompts 탭이 정렬해 보여줌 → 어떤 작업 패턴에 시스템이 자꾸 끼는지 파악.

### 10.3 LLM-as-judge — 정성 평가

수치 메트릭만으로는 "응답 품질 자체"를 못 잼. LLM이 prompt-응답 쌍을 0~10점으로 채점하는 방식이 LLM-as-judge.

```yaml
llm_judge:
  enabled: false
  backend: claude_cli                 # claude_cli | codex | manual
```

| Backend | 동작 | 장점 |
|---|---|---|
| **claude_cli** | `claude -p` 비대화 모드 호출 | claude code 구독 활용, API 키 불필요 |
| **codex** | `codex exec` 비대화 모드 | codex CLI 구독 활용 |
| **manual** | 콘솔 입력으로 사용자 직접 채점 | 외부 도구 의존 0 |

> **결정 발자취**: 처음엔 OpenAI API·ollama backend도 검토했으나 *"구독으로 다 되는데 굳이?"* 판단으로 3개로 단순화.

### 10.4 다음 — 진화 추적

## 11. 진화 추적

하네스 자체도 시간이 지나면서 변형된다 — Hard Rules가 추가되거나, plugin이 붙고 빠지거나, know-how가 검증되어 standard로 승격되거나. 이걸 인간 가독으로 추적·관리하는 게 12장.

### 11.1 자동 — `evolution/CHANGELOG.md`

`.harness/`를 git으로 관리 + post-commit hook이 매 커밋 후 diff 분석 → Keep a Changelog 표준으로 자동 갱신.

```markdown
## [2026-05-04 16:23 — commit abc1234]
### Added
- plugin: ralph
### Changed
- AGENTS.md: Hard Rules 1줄 추가
### Removed
- plugin: doc-driven-dev
```

분류는 **rule-based** (path 패턴 매칭). LLM 요약은 미래 옵션.

### 11.2 수동 — Snapshot

큰 마일스톤은 명시적으로 보존:

```bash
harness snapshot create v0.2 --reason "team rollout"
```

→ `evolution/snapshots/v0.2/`에 그 시점의 compose.yaml/AGENTS.md/tree.txt 복사. dashboard Evolution 탭에서 v0.1 ↔ v0.2 비교.

### 11.3 Publish 자격 검증 — know-how → standard

`know-how/`에서 충분히 검증된 자원을 글로벌 `standard/`로 승격할 때, 4 기준 검증을 거침:

| # | 자격 | 검증 |
|---|---|---|
| 1 | 항상 적용되어야 하는가 | 수동 (도메인 판단) |
| 2 | 압축되면 손해가 큰가 | 자동 (prefix 적합성, 4-블록 구조) |
| 3 | 짧게 표현 가능한가 | 자동 (크기 — 100KB 초과 시 경고) |
| 4 | 프로젝트 무관 보편적인가 | 수동 (도메인 판단) |

```bash
harness publish know-how/skills/my-helper --reason "...검증 결과..."
```

옵션:
- `--yes --reason "..."` 비대화 (CI 등). audit log 필수
- `--force` 모든 검증 우회 (위험)
- `--as <new-path>` 다른 이름으로
- `publishable.yaml` 사전 선언 (universal/always_applicable/reason)

모든 promote는 `evolution/publish-log.jsonl`에 audit log로 기록.

### 11.4 자식 → 부모 흐름

```
   know-how/skills/my-helper      (자식 클래스 — 자기 자원)
              │
              │ harness publish (자격 4기준 통과)
              ▼
~/.harness/standard/<mechanism>/my-helper  (모든 프로젝트가 발견 가능)
              │
              │ 다른 프로젝트가 사용:
              ▼
   <project>/.harness/compose.yaml 의 적절한 도메인 entry 에 `my-helper` id 추가
```

이 흐름이 12 요건 중 11번 — *하네스 자체가 진화 가능*.

## 12. Provider 어댑터

지금까지의 모든 hook은 **표준 envelope** (우리가 정한 JSON 포맷)을 기준으로 짜였다. 그런데 Claude Code·Codex·다른 도구마다 hook 시스템·envelope·등록 방식이 다 다름. 어댑터가 그 차이를 흡수해 표준 hook은 도구 무관하게 유지.

### 12.1 어댑터의 역할

```
[Provider별 envelope]                    [표준 envelope]
─────────────────────                    ─────────────────
Claude Code의 PreToolUse JSON              ┐
Codex의 어떤 포맷                       ───┼──→  표준 hook 입력
다른 도구의 또 다른 포맷                    ┘     ([입문 §10](01-입문.md#10-hook-시스템) 의 hook 시스템이 받는 것)

표준 hook 출력 (exit 2 + stderr / continue:false)
                                  ┌──→ Claude의 응답 처리
                                  └──→ Codex의 응답 처리
```

→ 새 provider 추가 = `register.sh` + `translate-*.sh` 작성만. 표준 hook은 한 줄도 안 건드림.

### 12.2 Claude Code 통합 (구체)

`<project>/.claude/settings.local.json`에 자동 등록:

```json
{
  "hooks": {
    "SessionStart":      [{"matcher": "*", "hooks": [{"type": "command", "command": "~/.harness/standard/adapters/claude/translate-start.sh"}]}],
    "UserPromptSubmit":  [{"matcher": "*", "hooks": [{"type": "command", "command": "~/.harness/standard/adapters/claude/translate-prompt.sh"}]}],
    "PreToolUse":        [{"matcher": "Edit|Write|NotebookEdit|Bash", "hooks": [...]}],
    "PostToolUse":       [...],
    "Stop":              [...]
  }
}
```

**왜 글로벌이 아닌 프로젝트 로컬?**: 글로벌 `~/.claude/settings.json`을 건드리면 다른 프로젝트에 의도치 않게 영향. 프로젝트 로컬은 격리 보장.

`translate-*.sh`가 jq로 envelope 변환 후 표준 hook 호출. claude는 stderr·exit code를 그대로 인식.

### 12.3 다른 Provider — Codex

`~/.harness/standard/adapters/codex/`는 placeholder 폴더만 있고 실구현은 사용 시점. 패턴은 claude와 동일:
1. `register.sh` — provider 설정 파일에 hook 등록
2. `translate-<event>.sh` — provider envelope ↔ 표준 envelope 변환

### 12.4 도구 중립 invariant

표준 envelope·표준 hook은 **provider 무관하게 안정**. 즉:
- claude · codex · 미래의 어떤 도구든 같은 hook이 같은 정책을 강제
- AGENTS.md / compose.yaml / 가드레일 / eval / viz 모두 그대로 동작
- 어댑터만 갈아끼우면 됨

### 12.5 마무리 — 전체 시스템 한 그림

```
[ 사용자 ]
  │
  │ compose.yaml 편집 (SSOT)
  ▼
~/.harness/standard/                  <project>/.harness/know-how/
  (검증된 기본 구성)                    (실험적 / 프로젝트 자산)
  · 7 메커니즘 폴더의 artifact 들       · 같은 7 메커니즘 구조 mirror
                  ↘                  ↙
                <project>/.harness/compose.yaml
                (5 도메인 × entry → 활성화 지도)
                            │
                            │ session_start hook
                            ▼
                  runtime/AGENTS.resolved.md
                            │
                            │ provider 어댑터 (translate-*.sh)
                            ▼
                  [ LLM 도구 — Claude / Codex / ... ]
                            │
                  ┌─────────┴──────────┐
                  ▼                    ▼
              도구 호출             응답 종료
              pre_tool_use 가         stop 의
              required / cognitive /  stop_validation 검증
              loop / context_gating
                  │
                  └─→ post_tool_use 가 trace 기록
                            │
                            ▼
                  분석 도구가 traces / decisions / metrics 를 읽음
                            │
                            ▼
                  evolution/CHANGELOG · snapshot
                  know-how → standard 승격
                  (시스템 자체의 진화)
```

이 한 그림이 모든 요소를 묶는다 — *standard · know-how 두 축*, *artifact 단위*, *7 메커니즘 × 5 도메인 × N:N*, *compose.yaml SSOT*, *hook 강제력*, *workflow 자동화*, *측정·진화*, *provider 무관 통합*.

## 14. 중급을 통달했다면

이 중급 문서를 끝까지 읽고 자기 프로젝트에서 위임·병렬·맥락·품질 axis를 활용해봤다면, 이제 *각 도구가 어떤 trade-off를 만드는지* 직접 느끼기 시작했을 것이다.

### 14.1 본 axis들의 trade-off (예시)

| 도구 | 얻는 것 | 잃는 것 |
|---|---|---|
| **Subagent 위임** | 부모 컨텍스트 정리, 병렬 가능 | sub-agent의 결과 통합 부담, 위임 비용 |
| **Worktree 병렬** | 진짜 병렬 throughput | per-session 가드레일이 합쳐 보지 못함 → 전체 변경 폭 통제 어려움 |
| **세션 횡단 컨텍스트** | 결정·함정 보존 | 잘못 보존되면 *영구적 오염* — 큐레이션 비용 |
| **Persona 라우팅** | 정밀한 포커스 | 라우팅 룰 자체가 새 부담, persona 간 일관성 유지 |
| **Multi-agent ensemble** | 사각지대 보완, 품질↑ | N배 비용, 합성 복잡도 |

각 axis는 *공짜가 아님*. 안전(입문) ↔ 성능(중급)의 trade-off를 *어디서 어떻게 잡을지*가 다음 단계.

### 14.2 → [My Harness System — 고급](03-고급.md)

고급은 다음 같은 질문에 답하는 단계:

- *"어떤 hook을 끄고 어떤 임계값을 올릴까?"*
- *"이 프로젝트엔 ensemble을 쓸 만한가, 비용이 큰가?"*
- *"여러 사람이 함께 쓰는 프로젝트에서 어떤 정책을 통일하고 어떤 걸 분기시킬까?"*
- *"하네스 자체를 어떻게 진화시켜갈까?"*

정답이 아닌 *상황별 trade-off* 정리 — 통달자만이 의미 있는 결정을 할 수 있는 영역. 자기 프로젝트에서 입문·중급의 도구를 *충분히 굴려봤을 때* 자연스럽게 다음 단계로 넘어가게 된다.

### 14.3 마무리 — 중급의 핵심

> *"위임 가능한 일은 빨리 위임하고, 맥락은 잃지 않게."*

입문이 *방어의 완성*이라면, 중급은 *방어를 깨지 않으면서 적극적으로 일을 분산·확장*하는 단계. 단일 에이전트의 안전을 갖추지 않은 채 위임·병렬에 들어가면 *폭주*하고, 위임 없이 안전만 추구하면 *느려진다*. 둘이 함께여야 중급의 본질이 살아남.
