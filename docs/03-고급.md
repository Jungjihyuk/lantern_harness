## 1부: 안전 ↔ 성능 Trade-off

> 입문(방어) ↔ 중급(성능)은 *별개*가 아니라 *같은 시스템의 두 면*이다. 한 쪽을 조이면 다른 쪽이 약해지고, 한 쪽을 풀면 다른 쪽이 위험해진다. 1부는 그 *충돌 지점들*을 정직하게 펼쳐놓는다.

## 1. Trade-off 메타 — 도구가 충돌하는 지점들

각 도구는 *공짜가 아니다*. 입문·중급에서 도구를 *얻는 것* 위주로 설명했지만, 통달자는 *잃는 것*도 보고 결정한다. 주요 충돌:

### 1.1 안전 ↔ 속도

| 도구 | 안전 효과 | 속도 효과 |
|---|---|---|
| Cognitive guard 빡빡 | 큰 변경 차단 → 안전↑ | 작업 자주 끊김, 분할 비용↑ → 속도↓ |
| Required Context 많음 | 정보 결핍 방지 → 안전↑ | 매번 Read 비용 → 속도↓ |
| Subagent 위임 | 부모 컨텍스트 깨끗 → 안전↑ | 위임·통합 비용 → *task 단위 속도↓*, *throughput↑* |
| Worktree 병렬 | (안전 효과 없음) | throughput↑ | per-session 가드레일이 *전체*를 못 봄 → 위험↑ |

→ "*어디까지 안전을 확보하고 어디서부터 속도를 택할지*" 결정 frame이 필요.

### 1.2 강제 ↔ 자율

| 도구 | 강제 정도 | 자율 영역 |
|---|---|---|
| `on_deny: hard_stop` | 매우 강제 (turn 즉시 정지) | 자가수정 불가 |
| `on_deny: self_correct` | 부드러움 (LLM이 stderr 보고 회복) | 자가수정 여지 큼 |
| `bypass_marker` | (한 번 통과) | 사람이 판단해 의도적 우회 |
| Stop validation `block` | 강제 (응답 못 끝냄) | 재시도 유도 |
| Stop validation `warn` | 약함 (경고만) | 사람·다음 단계가 처리 |

→ 너무 강제하면 *사람이 매번 결정*해야 → 흐름 끊김. 너무 자율이면 *방어 무력화*. 균형은 *작업의 위험도*에 따라.

### 1.3 정확성 ↔ 비용

| 도구 | 정확성 | 비용 |
|---|---|---|
| Multi-agent ensemble | 사각지대 보완 → 정확성↑ | N배 token |
| LLM-as-judge | 정성 평가 가능 | 채점 비용 (자동·수동) |
| Eval cases 많음 | regression 감지↑ | 매 변경 후 실행 시간 |
| 세션 횡단 컨텍스트 풍부 | 결정 일관성↑ | 큐레이션 비용, 잘못 보존 시 영구 오염 |

→ "*정확성을 어디까지 추구할 가치가 있는가*"는 작업의 *비용·중요도*가 결정.

### 1.4 단순함 ↔ 적응성

| 도구 | 단순함 | 적응성 |
|---|---|---|
| 하나의 compose.yaml | 단일 SSOT, 이해 쉬움 | 작업·환경에 따라 다른 정책 어려움 |
| Persona 라우팅 | (단순함 약화) | task별 정밀 적응↑ |
| Prefix 동적 조정 | (단순함 약화) | 컨텍스트 변화 적응↑ |
| 멀티 worktree | 폴더 격리·단순 | 일관성 통제 어려움 |

→ "*시스템을 단순하게 둘지, 적응력을 살릴지*"는 사용자 한 명인지 팀인지·프로젝트 크기·변동성 등에 좌우.

### 1.5 결정 frame — 4 질문

특정 도구를 *켤지·끌지·임계값을 어떻게 둘지* 고민될 때 다음 4 질문:

1. **이 작업의 위험도는?** — 큰 위험이면 안전·강제 우선 (예: 보안 코드 수정)
2. **이 작업의 비용은?** — 큰 비용이면 정확성에 투자 (예: 마이그레이션)
3. **이 작업의 빈도는?** — 빈번이면 자동·자율 우선 (예: 평범한 feature)
4. **이 결정을 누가 책임지나?** — 책임자가 명확하면 자율 가능, 모호하면 강제

이 4 질문에 답하면 *내 상황에서 어떤 trade-off가 맞는지* 거의 결정됨.

## 2. 가드레일 임계값 조정 — 언제 풀고 언제 조이나

입문 §9 의 cognitive guard 와 doom loop 는 *기본값* 으로 시작. 통달자는 그 임계값을 *프로젝트·시점에 따라 조정*한다.

### 2.1 임계값 결정 신호 — 데이터로 본다

직관으로 "조이자/풀자" 결정 X. **`decisions.jsonl`과 `viz improve`** 데이터로:

- **`cognitive_per_call` deny가 자주 발생 + 사용자가 매번 bypass 마커** → 임계값이 *너무 빡빡*. 상향 검토.
- **`cognitive_per_call` deny 거의 없음 + 큰 사고 발생** → 임계값이 *너무 풀어짐*. 하향 검토.
- **`loop_detection` 자주 발동 + 실제로 LLM이 막힘 패턴** → 임계값 적정. 그대로.

### 2.2 작업 단계별 임계값 분기

같은 프로젝트라도 *단계*에 따라 임계값이 달라야 자연스러움:

| 단계 | 권장 가드레일 | 이유 |
|---|---|---|
| 초기 prototyping | 풀어둠 (per_call 500+) | 빠른 실험 우선, 안전 비용↓ |
| Feature 개발 | 기본값 (per_call 200) | 균형 |
| Production 코드 변경 | 빡빡함 (per_call 100) | 사고 비용 큼 |
| 마이그레이션·리팩토링 | 빡빡 + bypass marker 의존 | 큰 변경이지만 *통제하면서* |

`compose.yaml`을 *영구 변경*하지 말고, **단계별로 임시 변경 + 끝나면 원복**이 안전 패턴. 또는 know-how로 fork해 단계별 compose.yaml 분기.

### 2.3 Stop validation — 매 응답 vs 단계 종료만

입문 §9 의 stop validation 은 *매 응답* 에 발동. 통달자는 이걸 *단계 종료 시*로 좁힐 수 있음:

```yaml
stop_validation:
  enabled: true
  on_fail: warn               # 일상은 warn만
  checks:
    - { command: "tsc --noEmit" }    # 가벼움 — 매 응답 OK
  # 무거운 검증은 ralph stage 끝에만
```

무거운 풀 테스트는 ralph stage chain의 *마지막 stage*에서 한 번만. 매 응답 강제하면 비용 폭발.

### 2.4 Hard rules — 무엇을 직접 박을지

AGENTS.md Hard Rules는 *압축 안 됨*이라 한 줄 비용이 큼. 너무 많으면 prefix 비대 → 컨텍스트 예산 잠식. 임계값:

- 5~7 줄 이상은 신호 — 일부를 trigger·on-demand로 옮길 검토
- *압축돼도 큰 손해 없는* 룰은 trigger로 lazy load
- *한 번도 어겨선 안 되는* 룰만 Hard Rules

## 3. 위임의 한계 — Subagent·Worktree의 숨은 비용

중급 1·2장에서 *위임·병렬*을 강조했지만, 통달자는 *위임이 안 맞을 때*도 안다.

### 3.1 Subagent가 손해인 경우

- **간단한 작업**: 위임 자체 비용이 작업보다 큼. 부모가 직접 하는 게 빠름.
- **컨텍스트 의존이 강한 작업**: sub-agent에게 컨텍스트를 옮기는 비용이 작업보다 큼.
- **결과 형태가 모호한 작업**: 부모가 결과를 통합하기 어려움 → 재호출·재작업
- **창의적·정성 판단**: sub-agent의 깨끗한 컨텍스트가 *부모의 누적된 직관*을 못 가짐

→ "**위임이 맞는지 의심되면 부모가 직접 한 번 해본다**" — 위임은 패턴이 명확할 때만.

### 3.2 Worktree 병렬의 숨은 위험

중급 2.4에서 짚은 *per-session 가드레일이 전체를 못 봄* 문제 + 추가 위험:

- **공유 자원 경쟁**: 두 worktree가 같은 파일·DB·외부 API를 동시 호출 — 충돌
- **Git 상태 혼선**: worktree A에서 만든 commit을 worktree B가 못 보거나 base 변경
- **인지 부하 폭발**: 사용자가 *진짜로* 두 작업을 동시에 따라가기 어려움 → 한 쪽이 방치
- **Cross-worktree 의존**: feature B가 feature A에 의존 시 — 직렬화 필요했던 것

→ Worktree는 **진짜 독립적인 두 작업**일 때만. 의존이 있으면 직렬이 더 빠름.

### 3.3 Multi-agent ensemble의 비용 임계점

Ensemble은 *N배 token*. 다음 신호일 때만:

- 결정 비용이 큼 (잘못된 답변의 손해 > 추가 토큰 비용)
- 단일 모델로 *합의가 잘 안 되는* 문제 (실제로 답변이 갈리는지 확인)
- 여러 모델이 *서로 다른 강점*을 가진 영역

자주 쓰는 ensemble은 *낭비*. 검증된 시점에만.

## 2부: 측정 기반 결정

> 1부의 trade-off는 *직관*만으로 결정하면 매번 다른 답이 나온다. 통달자는 **데이터로 결정**한다 — Eval·Viz·Improve가 그 도구.

## 4. 직관 대신 데이터 — Eval·Viz·Improve의 활용

입문·중급에서 본 측정 도구들을 *결정 입력*으로 쓰는 패턴.

### 4.1 임계값 결정에 Improve 활용

`harness improve`가 분석한 결과를 *그대로 따르지 말고* 신호로 해석:

```
[improve 결과 예시]
- cognitive_per_call deny+bypass가 마지막 30 prompt 중 12회 발생
  → 권장: max_diff_lines를 200 → 300으로 상향

[통달자의 판단]
- 12/30은 의미 있는 빈도. 단, *어떤 작업*에서 발생했는가 확인.
- prompts.jsonl 검사 → 모두 마이그레이션 작업이었음
- 결정: 영구 변경 X. 마이그레이션 단계만 임시 상향.
```

### 4.2 Regression 감지로 변경 판단

`harness viz eval`의 regression 알림은 *변경의 비용*을 가시화:

- compose.yaml 변경 후 일부 케이스 실패 → 변경이 *측정 가능한 손해*
- 이걸 *허용할 수 있는 손해*인지 판단 (다른 가치가 더 크면 OK)
- 허용 못하면 변경 reverse 또는 다른 방식

### 4.3 Bottleneck으로 위임 결정

`harness viz bottleneck` — 어떤 도구가 시간을 잡아먹는지:

- 한 도구 호출이 평균 5초 → sub-agent 위임 검토
- 같은 도구가 30번 호출 → batch·grep으로 한 번에 처리
- Provider 어댑터가 느림 → translate 스크립트 최적화 또는 다른 provider

### 4.4 Struggle score로 prompt 패턴 발견

`harness viz prompts` — struggle score 높은 prompt 패턴:

- 자주 막히는 prompt 패턴 → AGENTS.md Hard Rules에 *그 영역의 가이드* 직접 명시
- 같은 영역에서 반복 struggle → trigger·required context로 자동 강제

### 4.5 데이터를 보지 않는 결정의 위험

직관만으로 결정 시 가장 흔한 실수:
- *"내 느낌엔 가드레일이 빡빡한 것 같아"* → 데이터로는 별로 안 발동했음
- *"ensemble이 도움이 될 것 같아"* → 실제로 단일 모델 답변이 충분히 좋았음
- *"세션 공유가 필요해"* → 매 세션 같은 결정을 다시 하지 않았음

매번 *데이터 한 번* 확인 후 결정.

## 5. LLM-as-judge로 정성 결정 보강

수치(eval pass rate, deny count)만으로는 *답변 품질·정성*을 못 잼. LLM-as-judge가 그 부분 보완.

### 5.1 언제 judge가 의미 있나

- **정성 답변의 품질 비교**: ensemble의 두 답변 중 어느 게 좋은지
- **Persona 효과 측정**: persona on/off 시 답변이 실제로 더 *집중*돼졌는지
- **Hard Rules 효과**: 룰 추가 후 답변이 정말 그 룰을 따르는지

### 5.2 backend 선택의 trade-off

| Backend | 비용 | 정확성 | 적정 |
|---|---|---|---|
| `claude_cli` | 구독 안에서 / 외부 비용 0 | 높음 (claude 모델) | 일상 채점 |
| `codex` | 구독 안 / 0 | 중간~높음 | 다른 시각 비교 |
| `manual` | 사용자 시간 비용 | 가장 높음 | 핵심 결정 |

매 응답 자동 채점은 비용·노이즈 큼. **수동 트리거**(`harness judge run`) — 의문이 들 때만.

### 5.3 Judge의 한계

- LLM이 LLM을 채점 — *같은 사각지대* 공유 가능
- Judge prompt 자체가 결과를 좌우 (말 한 마디 차이로 점수 흔들림)
- 정량화 어려운 "더 좋다"를 숫자로 만드는 건 본질적으로 손실

→ Judge는 *결정 입력의 한 신호*, *정답이 아님*. 사람의 마지막 판단이 필요.

## 6. 단일 사용자에서 팀으로 — 새로 등장하는 문제들

혼자 쓸 땐 안 보이던 것들이 *둘 이상*에서 폭발.

### 6.1 정책 일관성 vs 자율

- 모든 팀원이 *같은 compose.yaml*: 일관성↑, 개인 작업 스타일 무시
- 각자 *자기 compose.yaml*: 자율↑, 팀 단위 정책 누수
- **타협**: standard 영역(글로벌 `~/.harness/standard/`)은 통일, know-how는 자유

### 6.2 Know-how 충돌

- 팀원 A가 만든 know-how가 B의 작업에 *방해*가 됨
- 같은 path를 다르게 override
- **해결**: know-how는 *프로젝트별 commit*하고, 팀 전체가 보는 부분은 명시적 *standard*로 publish

### 6.3 세션 횡단 컨텍스트의 오염

`runtime/shared/`에 한 사람이 잘못된 결정 promote → 모든 팀원의 세션에 prefix로 박힘.
- **해결**: shared store는 *PR 리뷰 거쳐 commit*. 자동 추가 X.

### 6.4 Eval·평가 기준의 표준화

- A가 *내 기준엔 통과*인 케이스가 B에겐 *부족*
- **해결**: eval 케이스도 *팀 합의*로 표준화. 통달자가 가이드.

### 6.5 진화의 속도

혼자 쓸 땐 *마음대로 빠른 진화* 가능. 팀에선 매 변경이 *모두에게 영향*.
- **해결**: snapshot으로 마일스톤 명시 + CHANGELOG 리뷰 + 큰 변경은 *통달자 사인*

## 7. 정책 통일 vs 분기 — Fork·Publish 전략

조직에서 *어디까지 통일하고 어디서부터 분기*할지의 전략.

### 7.1 통일 영역 — `~/.harness/standard/`

조직 단위로 통일할 만한 것:
- hook 시스템 (모든 프로젝트가 같은 7 hook artifact 와 envelope 규약)
- Cognitive guard·loop detection 메커니즘 자체
- Eval runner·viz·improve 도구
- Provider 어댑터

이건 *standard* 에 두고 모든 프로젝트가 compose.yaml 의 id entry 로 참조.

### 7.2 분기 영역 — 프로젝트별 know-how

- AGENTS.md 본문 (각 프로젝트의 정의·룰)
- Required Context paths
- 임계값 (cognitive_guard 등)
- Persona·trigger 라우팅

이건 *know-how*로 자유 분기.

### 7.3 Fork 시점 — *임시 변형*

know-how 에 **다른 id** 로 fork artifact 를 만들고 compose 에서 그 id 를 활성화. 그 시점부터 standard 와 분리됨. 신중히:
- 팀이 *모두* 동의한 변형만 fork
- Fork 후 검증되면 *그 변형을 publish해 standard로 승격*
- Fork 상태로 오래 두지 말 것 — 글로벌과 drift

### 7.4 Publish 시점 — *조직 표준 승격*

`harness publish` 4 자격 기준 (보편성·압축 손해·짧음·항상 적용)에 더해 *조직 단위 추가 기준*:
- 최소 N개 프로젝트에서 검증됨
- 통달자 리뷰 통과
- audit log에 *왜 표준화했는지* 명확히 기록

### 7.5 Publish 거부 패턴

- 한 프로젝트만 쓰는 know-how → publish X
- 빈도가 낮은 know-how → publish X (사용 안 되면 standard 비대화)
- 규약은 옳으나 *적용이 어려움*하면 standard보다 *문서·교육*이 적정

## 4부: 자가 진화 — 도전 과제

> 자가 진화는 *목표* 가 아니라 *결과*. 아직 정립된 스탠다드는 없고, 우리 철학을 바탕으로 어디까지 가능하고 어디까지 위험한지 살펴본다.

## 8. 자가 진화 — 도전 과제

> *시스템이 자기 자신을 갱신하는* 영역. 아직 정립된 스탠다드는 없고, 우리 철학 (인지 한계 안의 안전 · 검증된 결정만 보존) 을 바탕으로 어떤 시도들이 있고 앞으로 어디로 가야 할지 정리.

### 8.1 자가 진화란 무엇인가 — 정의와 우리 철학

**정의**: 시스템 (compose · standard · know-how · 정책 · prompt) 이 *자기 자신을 갱신* 하는 과정. 사람이 매번 갱신하지 않아도 작동 패턴 + 측정 데이터로부터 자동 개선.

**왜 도전 과제 인가:**

| 어려움 | 본질 |
|---|---|
| 잘못된 자가 결정의 risk | LLM 이 자기 시스템을 잘못 수정하면 안전판이 함께 무너짐 |
| 검증 가능성 | "이 자가 진화가 좋은 진화인가" 를 무엇으로 판단할지 — eval 만으로는 부족 |
| 일반화 | 한 프로젝트의 학습이 다른 프로젝트에 도움 되는가, 해 되는가 |
| 표준 부재 | 업계가 아직 "자가 진화 = 이렇게 한다" 합의가 없음 |

**우리 철학** ([입문 §14.3](01-입문.md#143-한-줄로) 의 한 줄): *"내 인지 한계를 넘는 일은 LLM 에게도 시키지 않는다."*

자가 진화에서도 같다 — 사람의 검증 능력을 넘는 자가 변경은 허용하지 않는다. 자동 적용은 작은 단위, 큰 단위는 사람이 승인. *ratchet* — 한 단계씩 검증된 것만 누적되고 뒤로 가지 않음.

### 8.2 이미 우리가 가진 진화 메커니즘

자가 진화의 *기록 · 제안* 까지는 시스템에 갖춰져 있다. *자가 적용* 만 미정.

**(a) `know-how → standard` 승격 — publish 흐름**

know-how 에서 자란 자산이 자격 (보편적 · 검증됨 · 중립성) 을 통과하면 standard 로 옮긴다. 가장 명시적인 진화 메커니즘 — 사람이 결정하지만, 자격 검증은 자동.

**(b) traces · decisions 누적 → improve 의 룰 기반 제안**

매 세션의 hook 결정 · 도구 호출이 `runtime/sessions/<id>/` 에 누적. `improve` 가 패턴을 분석해 *"이 가드 임계값 너무 빡빡 / 이 trigger 안 걸림"* 같은 제안 카드 출력. 사람이 승인 → compose.yaml 갱신.

**(c) eval verdict + regression 감지**

매 변경 후 eval 회귀 테스트. 점수가 떨어지면 *"이 변경은 진화 아님"* 자동 표시. 진화의 *반대 방향* 자동 감지.

**(d) `evolution/CHANGELOG.md` 자동 추적**

git post-commit 이 `.harness/` 의 모든 변경을 자동 기록. *어떻게 진화해왔는가* 의 ratchet 효과 — 뒤로 가려면 무엇이 사라지는지 명확해짐. Snapshot 으로 *큰 단위 단계* 도 가능.

**(e) 의도된 정체 (intentional plateau)**

진화 *안 하는 것* 도 진화의 한 형태. 빠른 변경이 안 좋을 때 정책을 굳혀 *고의로 정체* 시키는 패턴. 신뢰성 우선 시점에 사용.

### 8.3 외부 SOTA — 어떤 시도들이 있나

업계의 다양한 자가 진화 시도들. 각각이 *우리 시스템의 어느 메커니즘과 매핑* 되는가:

| 시도 | 핵심 idea | 우리 시스템 매핑 |
|---|---|---|
| **Reflexion / Self-Refine** | LLM 이 자기 응답을 비평 · 재시도 | `judge` + self_correct decision (한 세션 안 자가 보정) |
| **Voyager** (Minecraft skill library) | skill 을 자동 누적해 다음 작업에 재사용 | `know-how/tools/` · `know-how/workflows/` 자동 적재 — 검증된 패턴이 standard 로 승격 |
| **Self-improving prompts** (DSPy, TextGrad) | prompt 자체가 사용 패턴 보고 자기 갱신 | `cognition.instructions` 본문이 traces 분석으로 자동 다듬어짐 |
| **AutoGPT / BabyAGI** | 자가 task 분해 + 실행 | ralph workflow 의 stages 가 자동 생성 · 확장 |
| **Memory-augmented agents** (MemGPT 등) | long-term memory 가 학습 누적 | `runtime/shared/` 자동 promote — *검증된* 결정만 |

**공통 패턴**: 모두 *측정 → 제안 → 적용* 의 루프. 차이는 *어느 단계까지 자동* 인가.

### 8.4 발전 방향 — 단계별 접근

자가 진화의 *안전한 단계 적층*:

| Step | 내용 | 자동화 정도 | 현재 상태 |
|---|---|---|---|
| 1. 측정 자동화 | traces · decisions · eval 누적 | 완전 자동 | ✅ 있음 |
| 2. 제안 자동 생성 | 패턴 분석으로 *"이렇게 바꾸자"* 제안 | 자동 (rule-based) | ✅ improve |
| 3. 자동 적용 (한정) | 사용자 승인 후 작은 영역만 자동 patch | 사용자 승인 + 좁은 영역 | 🔄 부분 |
| 4. 자가 검증 | 자동 적용 후 eval + judge 가 검증 | 자동 | 🔄 부분 |
| 5. 자가 진화 루프 | 자가 진화 자체가 진화 (메타) | 매우 한정 | ❌ 미정 |

**각 단계의 안전 가이드:**

- Step 3 의 *자동 적용 범위* 가 가장 위험한 결정. 우리 철학에선 *사람의 검증 가능 영역* 안에서만 — 예: 가드 임계값 한 줄 조정 OK, hook 로직 통째 재작성 NO.
- Step 4 자가 검증의 *자가 검증 trap* — 자가 진화가 자기 진화를 좋다고 평가하는 함정. 외부 anchor (사용자 만족도, 사고 빈도) 가 필요.
- Step 5 메타 진화는 *완전 미정 영역*. 시도하지 말라는 의미가 아니라, 시도 시 *안전판이 시스템 밖에* 있어야 한다 (예: 외부 사람의 정기 audit).

### 8.5 안 풀린 문제들 + 마무리

업계가 함께 풀어야 할 큰 물음들:

| 문제 | 어려움 |
|---|---|
| 잘못된 자가 결정 감지 | "이 자가 변경은 좋은가" 의 ground truth 가 없음. 측정 자체가 진화 대상이라 자가 검증 trap. |
| 프로젝트 일반성 | 한 프로젝트에서 좋은 진화가 다른 프로젝트에선 해 — 일반화 신호 어떻게 |
| 사람과의 인터페이스 | 어디까지 자동, 어디서 멈출지 — 사람의 부담 vs 자동의 risk |
| 진화 속도 vs 안정성 | 빨리 적응 vs 충분히 검증 — 같은 시스템 안에 두 axis 가 충돌 |

**마무리 — 우리가 어떻게 가져갈지:**

자가 진화는 *목표* 가 아니라 *결과*. 측정 · 제안 · 검증의 메커니즘이 잘 깔려 있으면 진화는 따라온다. 빨리 가려고 단계를 건너뛰면 시스템 자체가 위험.

> *"시스템을 빚는다."* — 통달자는 자가 진화의 자동 적용을 늘리는 게 아니라, **자가 진화가 안전한 영역을 천천히 넓혀가는** 사람.

이 부의 도전 과제 framing 자체가 *우리도 답이 없다* 의 정직한 인정 — 사용자가 자기 운영에서 발견하는 패턴이 새로운 표준이 될 가능성. 함께 빚는 영역.

## 5부: 운영 사례 (Patterns)

> 추상 원칙은 1·2·3부에서 다 봤다. 4부는 *구체적 시나리오*에서 그 원칙들이 *어떻게 결합되는지*. 사례는 가설적 — 통달자가 자기 사례로 채워가야.

## 9. 사례 — 큰 마이그레이션

### 9.1 시나리오

- 50+ 파일에 걸친 ORM 라이브러리 교체
- 변경 폭이 입문 cognitive guard 임계값(per_session 1000 lines)을 훨씬 넘김
- 한 번에 다 안 됨. 단계별 마이그레이션 + 회귀 테스트 필수

### 9.2 통달자의 결정 흐름

1. **Worktree 분리** — 기존 master는 그대로, 마이그레이션은 새 worktree에서 (사고 시 격리)
2. **단계별 compose.yaml 임시 변경** — `cognitive_guard.per_session.max_diff_lines: 5000` 임시 상향
3. **Ralph stage chain** — 5 단계 (1: schema, 2: read paths, 3: write paths, 4: tests, 5: docs)
4. **각 stage 끝에 stop_validation `block`** — 단계 검증 미통과면 다음 단계 X
5. **Multi-agent ensemble은 stage 5(docs)만** — 나머지는 단일 모델
6. **Eval 케이스 사전 추가** — 마이그레이션 전 baseline 측정
7. **마이그레이션 끝나면 compose.yaml 원복** — 임계값 다시 빡빡하게

### 9.3 회고 항목

- 어떤 stage가 가장 오래 걸렸나 → bottleneck viz로 확인
- Multi-agent가 가치 있었나 (docs stage) → judge 점수 비교
- 잘못 마이그레이션된 부분이 있었나 → eval regression
- 시간 vs 안전 trade-off는 적정했나 → 다음 마이그레이션의 input

## 10. 사례 — Multi-agent 도입

### 10.1 시나리오

- 단일 모델로 운영하던 프로젝트에 multi-agent ensemble 도입
- 주제: 아키텍처 결정 (마이크로서비스 vs 모노리스)

### 10.2 통달자의 결정 흐름

1. **Manual judge로 시작** — ensemble 결과를 *사람이* 채점. 비용 0, 신뢰↑
2. **명확한 비교 prompt 준비** — 같은 입력을 두 모델에 보냄
3. **Aggregator는 단순하게** — 각 답변 + 사용자 비교 노트만 출력 (자동 합성 X)
4. **검증 후에만 자동화** — manual로 N번 만족스러우면 `claude_cli` 또는 `codex` backend로 자동 채점
5. **비용 임계값 설정** — 월 예산 (예: $100) 넘으면 알람

### 10.3 회고 항목

- 두 모델이 *실제로 다른 답변*을 했나 (단일 모델로 충분했을지)
- 합성 답변이 *어느 한 모델의 답변보다 나았나*
- 비용 vs 가치 — ROI 측정

## 11. 사례 — 사고와 복구

### 11.1 시나리오

- compose.yaml 변경 후 모든 hook이 동작 안 함
- 새 세션이 가드레일 없이 시작 → 큰 변경 commit됨

### 11.2 통달자의 복구 흐름

1. **즉시 격리** — `harness unlink claude` (provider 등록 해제) → 더 이상 hook 미발동
2. **Snapshot으로 복원** — 가장 가까운 정상 snapshot으로 compose.yaml·standard 복원
3. **사고 commit 분석** — git log + diff로 영향 범위 확인
4. **사고 commit 처리 결정** — revert / 부분 보존 / 통째로 다시 작성
5. **Hook 재등록 + doctor** — `harness link claude && harness doctor` 통과 확인
6. **사고 원인 분석** — compose.yaml의 어떤 변경이 hook 무력화? 어떤 검증이 빠졌나?
7. **재발 방지** — eval 케이스 추가 (같은 형태의 compose.yaml은 거부) + audit log

### 11.3 회고 항목

- 사고가 일어나기까지 *경고 신호*가 있었나 (ignored or 못 봄)
- doctor가 사고 *이후*가 아니라 *이전*에 잡았어야 함 → doctor 체크 보강
- 진화 추적(CHANGELOG)이 사고 commit에 의미 있는 정보를 담았나
- 팀 단위 운영이라면 — *사고 영향이 다른 사람에게 어떻게 퍼졌나*

## 6부: 마무리

## 12. 통달자의 자세

### 12.1 정답이 없다는 사실의 수용

입문·중급은 *도구의 사용법*. 고급에서 정답은 없다 — 같은 도구가 *상황에 따라* 켜야 할 때도 끌 때도 있다. 이걸 *받아들이는 것*이 통달의 시작.

> *"이 가드레일은 빡빡해야 한다"* (X)
> *"이 작업·이 시점·이 사람에게는 빡빡해야 한다"* (O)

### 12.2 측정 우선 — 직관은 입력일 뿐

직관이 *왜 그렇게 느끼는지*를 데이터로 검증. 직관이 맞을 수도 있고 틀릴 수도 있음. *"느낌"으로* 결정하지 말 것.

### 12.3 작은 단위로 변경, 큰 단위로 회고

매 변경은 *작게*. 영향 범위 명확. 회고는 *주기적·큰 단위*로 — 패턴 발견.

### 12.4 시스템을 *빚는다*는 자세

시스템은 *완성된 것*이 아님. 통달자는 시스템을 *주조하는 사람*. 입문·중급의 도구는 재료, 고급의 trade-off 판단은 *조각*.

### 12.5 다음 사용자에게 물려줄 것

자신의 통달이 *자기에게만 머물면* 손실. 통달자가 발견한 패턴·trade-off는 *문서·snapshot·publish*로 다음 사용자에게:

- 진화 CHANGELOG에 *왜 그 결정을 했는지* 기록 (*무엇을 했나*가 아니라)
- 운영 사례 추가 — 5부의 §9·§10·§11 처럼 자기 시나리오로 채움
- Publish할 때 *audit log에 정직하게*

### 12.6 한 줄로

> *"Trade-off를 직접 조절해 내 시스템을 빚는다."*

도구를 알았으면 (입문), 위임할 수 있게 됐으면 (중급), 이제는 *어디까지 자기 시스템으로 만들지*를 결정하는 단계. 매 결정에 *책임*과 *재미*가 있다 — 통달자만이 이 둘을 모두 즐길 수 있다.
