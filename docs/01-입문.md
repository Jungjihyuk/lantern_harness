## 1. 글로벌 루트 — `~/.harness/`

도구·프로젝트 무관하게 시스템에 한 번만 깔리는 글로벌 자원. 모든 프로젝트가 여기를 공유.

```
~/.harness/
│
├── bin/                            # CLI 실행파일들 (PATH에 등록되는 곳)
│   ├── harness                     # 엔트리 스크립트 — 모든 명령의 dispatcher
│   └── cmd/                        # 각 서브명령 구현 (16개)
│       ├── init.sh                 # 프로젝트 부트스트랩
│       ├── link.sh / unlink.sh     # provider hook 등록/해제
│       ├── list.sh                 # plugin 목록
│       ├── install.sh / remove.sh  # 글로벌 → 프로젝트 symlink
│       ├── fork.sh                 # symlink → 로컬 복사 (수정 가능)
│       ├── publish.sh              # know-how → 글로벌 promote (자격 검증)
│       ├── scaffold.sh             # README/SECURITY/DESIGN/CONVENTIONS 빈 뼈대
│       ├── viz.sh                  # 6 viz 렌더러
│       ├── eval.sh                 # 회귀 테스트
│       ├── improve.sh              # 사용 패턴 분석 + 개선 제안
│       ├── judge.sh                # LLM-as-judge 수동 트리거
│       ├── ralph.sh                # 무인 루프 시작/상태/리스트
│       ├── reload.sh               # resolved.md 재생성
│       ├── doctor.sh               # 환경 진단
│       └── version.sh
│
├── standard/                       # "부모 클래스" — 도구·도메인 중립 표준 자원
│   │                               #   누구든 가져다 쓸 수 있는 검증된 기본값
│   │                               #   프로젝트는 이걸 symlink로 참조
│   │
│   ├── AGENTS.md                   # 표준 AGENTS.md 템플릿 (4 블록 구조)
│   │                               #   compose.yaml 부재 시 fallback으로도 사용
│   │
│   ├── README.md                   # 사람용 설명
│   │
│   ├── hooks/                      # 표준 5-hook plugin (Claude 이벤트 이름과 통일)
│   │   │                           #   session_start / user_prompt_submit /
│   │   │                           #   pre_tool_use / post_tool_use / stop
│   │   ├── session_start.sh        # SessionStart — AGENTS.md 주입·status 초기화
│   │   ├── user_prompt_submit.sh   # UserPromptSubmit — 가드레일·prompts.jsonl 기록
│   │   ├── pre_tool_use.sh         # PreToolUse — Required·trigger·loop·cognitive 검사
│   │   ├── post_tool_use.sh        # PostToolUse — status·trace·timing 갱신
│   │   ├── stop.sh                 # Stop — 응답 완료 전 작업 검증 (stop_validation)
│   │   ├── post_commit.sh          # git post-commit (Evolution CHANGELOG 자동 갱신)
│   │   └── lib/                    # 공통 helper
│   │       ├── common.sh           # 공통 함수 (status, trace, decision_log, timing)
│   │       ├── policy.py           # compose.yaml 파싱 + AGENTS.md 생성 + trigger 매칭
│   │       └── evolution.py        # CHANGELOG 자동 갱신 로직 (rule-based)
│   │
│   ├── ralph/                      # 무인 루프 러너 plugin
│   │   ├── runner.sh               # 메인 loop
│   │   ├── stuck_detect.sh         # Doom loop 감지
│   │   ├── verify.sh               # default verify (override 대상)
│   │   ├── task-template.md        # task 작성 양식
│   │   ├── invokers/               # Provider별 agent 호출 매개체
│   │   │   ├── manual.sh           # 사용자 mediation (default, 안전)
│   │   │   └── claude.sh           # claude --print 비대화 모드
│   │   └── lib/state.py            # ralph run 상태 (JSON) 관리
│   │
│   ├── adapters/                   # Provider 어댑터 (claude 구체, codex placeholder)
│   │   │                           #   표준 hook을 각 provider hook 시스템에 매핑
│   │   └── claude/
│   │       ├── register.sh         # settings.local.json에 5 hook 자동 등록
│   │       ├── unregister.sh
│   │       ├── translate-start.sh    # SessionStart 이벤트 변환
│   │       ├── translate-prompt.sh   # UserPromptSubmit 이벤트 변환
│   │       ├── translate-pre.sh      # PreToolUse 이벤트 변환
│   │       ├── translate-post.sh     # PostToolUse 이벤트 변환
│   │       └── translate-stop.sh     # Stop 이벤트 변환
│   │
│   ├── templates/                  # 흔한 프로젝트 문서 빈 뼈대
│   │   ├── README.md               # `harness scaffold`로 프로젝트에 복사
│   │   ├── SECURITY.md
│   │   ├── DESIGN.md
│   │   └── CONVENTIONS.md
│   │
│   ├── skills/                     # 승격된 skill 거주지 (`harness publish`로 옴)
│   │
│   └── eval/                       # 회귀 테스트 케이스 (글로벌)
│       └── cases/                  # *.yaml — 우리 hook이 잘 동작하는지 검증
│           ├── required-deny.yaml
│           ├── required-allow-after-read.yaml
│           ├── required-hard-stop.yaml
│           ├── cognitive-guard-per-call.yaml
│           └── loop-detection.yaml
│
├── lib/                            # 시각화·분석용 Python 모듈
│   │                               #   bash로 짜기엔 무거운 로직만 여기 (PyYAML 외 표준 라이브)
│   ├── viz/                        # 시각화
│   │   ├── main.py                 # 6 viz 렌더러
│   │   │                           #   (workflow/subagents/bottleneck/eval/improve/prompts)
│   │   │                           #   workflow는 compose.yaml의 hook 토글 동적 반영
│   │   └── dashboard.py            # 라이브 HTTP 대시보드 (SSE + 인터랙티브 편집)
│   ├── eval/
│   │   └── runner.py               # eval 케이스 실행 + 결과 누적

│   ├── prompts/                    # prompt struggle score 분석
│   │   └── main.py                 # denies×2 + retries×3 + duration_s/10 + bypass×1
│   └── judge/                      # LLM-as-judge
│       ├── main.py                 # judge 엔트리
│       └── backends.py             # 3 backend dispatch (claude_cli / codex / manual)
│
├── know-how/                       # 글로벌 know-how (옵션, 모든 프로젝트 공통 적용)
│                                   #   대부분 비어있음 — 프로젝트별 know-how가 일반적
│
└── registry.yaml                   # plugin 카탈로그 (UI 검색용 — 미래 확장)
```

### 핵심 원칙

- **standard는 "부모 클래스"**: 모든 프로젝트의 공통 기본값. 손대면 모든 프로젝트에 영향.
- **lib는 도구**: bash로 짜기 무거운 로직 (시각화·분석)만 Python으로.
- **bin은 진입점**: 사용자가 PATH로 부르는 곳. 실제 로직은 standard/lib에 위임.
- **adapters는 격리**: Provider별 차이는 어댑터가 흡수, 표준 hook은 도구 무관.
- **글로벌은 share, 프로젝트는 customize**: 프로젝트의 `.harness/` (별도 문서)가 standard를 symlink로 참조하면서 know-how로 override.

## 2. 프로젝트 단위 — `<project>/.harness/`

`harness init` 실행 시 프로젝트 디렉토리에 생성. 각 프로젝트마다 독립적.

```
<project>/.harness/
│
├── compose.yaml                     # SSOT — 이 파일만 편집하면 동작·정책 다 바뀜
│                                   #   mode·prefix·plugins·hooks 토글·required_context·
│                                   #   trigger_read·hard_rules·cognitive_guard·loop_detection·
│                                   #   stop_validation·llm_judge·ralph 다 여기
│
├── README.md                       # newbie용 1분 가이드 (init 시 자동 생성, 자유 편집)
│
├── standard/                       # ~/.harness/standard/ 로의 symlink (수정 X)
│   ├── AGENTS.md → ~/.harness/standard/AGENTS.md
│   └── hooks    → ~/.harness/standard/hooks
│                                   # `harness fork <name>` 하면 symlink → 로컬 복사로
│                                   #   변환됨 (그 후엔 수정 OK, 글로벌 영향 X)
│
├── know-how/                       # "자식 클래스" — 자기 노하우 자유 편집 (gitignore 가능)
│   ├── AGENTS.md                   # standard/AGENTS.md 통째 override (선택)
│   ├── DESIGN.md                   # 새 표준 md (compose.yaml.prefix에 추가하면 prefix)
│   ├── hooks/
│   │   ├── session_start.sh        # standard hook 통째 override
│   │   └── session_start.d/        # standard hook 후 chain 실행 (UNIX .d/ 패턴)
│   │       ├── 10_log.sh
│   │       └── 20_extra.sh
│   ├── skills/
│   │   ├── my-skill-1/SKILL.md
│   │   └── my-skill-2/SKILL.md
│   ├── ralph/
│   │   ├── verify.sh                # standard ralph verify override
│   │   ├── ralph-task.md            # ralph 단일 task 명세 (모드 A)
│   │   └── ralph-stages.yaml        # stage chain 명세 (모드 B)
│   ├── eval/
│   │   └── cases/                   # 프로젝트만의 회귀 테스트 케이스
│   └── (기타 자유)
│
├── runtime/                        # 자동 생성 (gitignore 권장)
│   ├── AGENTS.resolved.md          # compose.yaml로부터 매 세션 자동 생성된 결과
│   ├── traces/<session-id>.jsonl   # 도구 호출·session_start·stop 등 trace
│   ├── sessions/<session-id>/
│   │   ├── meta.json                # transcript_path, started_at 등
│   │   ├── prompts.jsonl            # user_prompt_submit이 기록 (질문 텍스트)
│   │   ├── decisions.jsonl          # pre_tool_use 결정 (allow/deny + 이유)
│   │   ├── required-status.json     # Required Context 읽음 추적
│   │   ├── cognitive-guard.json     # 누적 변경 파일·라인
│   │   ├── timing.json              # tool 시작 시각 (pre→post diff용)
│   │   └── judge.jsonl              # LLM-as-judge 점수 (실행 시)
│   ├── ralph/
│   │   ├── active.lock              # 동시 ralph 방지
│   │   └── runs/<run-id>/           # ralph 한 번의 실행 기록
│   ├── eval-results/<ts>.json       # eval 실행 결과 누적
│   └── viz/<type>-<ts>.html         # `harness viz --format=html` 출력
│
├── evolution/                       # git tracked — 진화 이력
│   ├── CHANGELOG.md                 # post-commit hook이 자동 갱신
│   └── publish-log.jsonl            # `harness publish`의 audit log
│
└── .claude/                         # claude code의 프로젝트 settings (link 시 자동)
    └── settings.local.json          # `harness link claude`가 hook 등록한 곳
                                     #   (글로벌 ~/.claude/settings.json 안 건드림)
```

### 핵심 원칙

- **편집할 곳은 단 하나, `compose.yaml`** — SSOT. AGENTS.md·hook 동작·가드레일 임계값 등 모든 정책.
- **`standard/`는 손대지 말 것** — symlink라 수정 시 글로벌 영향. 변형 필요하면 `harness fork`.
- **`know-how/`는 자유** — OOP 자식 클래스. 같은 path는 override, `<name>.d/`는 chain.
- **`runtime/`은 일회성** — 매 세션 새로 생성. gitignore. 분석 도구가 여기 데이터를 읽음.
- **`evolution/`은 영구 이력** — git에 commit. 어떻게 진화해왔는지 추적.
- **`.claude/settings.local.json`은 어댑터 등록부** — `harness link claude`가 자동 작성·갱신. 직접 손대지 않아도 됨.

## 3. 두 레이어가 결합되는 방식

### 3.1 OOP 상속 비유

가장 정확한 멘탈 모델은 **클래스 상속**이다.
※ **멘탈 모델**: _사용자가 현재 사용 중인 시스템(웹, 앱 또는 기타 제품)에 대한 개인적인 이해와 믿음_

| OOP | 하네스 |
|---|---|
| 부모 클래스 | `~/.harness/standard/` |
| 자식 클래스 | `<project>/.harness/know-how/` |
| 그대로 상속 | know-how에 파일을 만들지 않음 → standard가 그대로 적용 |
| 메서드 override | `know-how/<같은 path>` → standard 무시, 내 것 사용 |
| `super().method()` 후 추가 | `know-how/<hook>.d/*.sh` → standard 실행 후 chain |
| 자식만의 새 멤버 | `know-how/MY-EXTRA.md` (standard에 없는 새 파일) |
| 자식 → 부모 promote | `harness publish <path>` |

이 비유는 단순한 설명용이 아니라 **시스템이 실제로 그렇게 동작**한다. 우선순위 알고리즘은 단 한 줄로 표현된다:

> 같은 path가 know-how에 있으면 standard를 가린다 (override). `.d/`에 있으면 standard 뒤에 추가 실행 (chain). 둘 다 없으면 standard 그대로.

### 3.2 결합의 세 모드

폴더 한 단계씩 들어가면서 보면, 결합은 결국 **세 가지 중 하나**다.

```
[모드 A: 상속]      know-how/foo.md 없음
                    └→ standard/foo.md 그대로 사용

[모드 B: override]  know-how/foo.md 있음
                    └→ standard/foo.md 무시, know-how/foo.md 사용

[모드 C: chain]     know-how/foo.d/10_x.sh, 20_y.sh 있음 (hook 한정)
                    └→ standard/foo.sh 먼저 실행, 이어서 10_x.sh → 20_y.sh
                       (알파벳 순)
```

세 모드의 적용 대상:

| 자원 종류 | 모드 A (상속) | 모드 B (override) | 모드 C (chain) |
|---|:---:|:---:|:---:|
| AGENTS.md (md 파일) | ✓ | ✓ | — *(폴더 chain 대신 prefix 리스트 사용 — 아래 설명)* |
| Hook 스크립트 | ✓ | ✓ | ✓ |
| Skill | ✓ | ✓ | — |
| Ralph verify·task | ✓ | ✓ | — |

#### MD 파일은 왜 `.d/` chain이 없나 — `compose.yaml.prefix` 리스트가 그 역할

Hook은 "실행되는 함수"라 `<name>.d/*.sh`로 알파벳 순 누적이 자연스럽지만, MD는 "노출되는 텍스트"이고 **어떤 문서를 어떤 순서로 LLM prefix에 넣을지**를 사용자가 명시적으로 결정하고 싶은 자원이다. 그래서 폴더 chain 대신 `compose.yaml`의 `prefix:` 리스트로 명시한다:

```yaml
# <project>/.harness/compose.yaml
prefix:
  - AGENTS.md                    # standard/AGENTS.md (또는 know-how/AGENTS.md가 있으면 그것)
  - know-how/SECURITY.md         # know-how가 추가한 새 md
  - know-how/COMPANY-RULES.md    # 또 다른 추가 md
```

이 리스트가 LLM의 system prefix로 **위에서 아래 순서대로 누적 주입**된다. 즉 MD 영역의 "chain"은 폴더가 아니라 **YAML 리스트의 항목 순서**로 표현됨.

**결과적으로 가능한 시나리오들**:

| 하고 싶은 것                     | 어떻게                                                              |
| --------------------------- | ---------------------------------------------------------------- |
| standard AGENTS.md 그대로 쓰기   | know-how 비워두기 (모드 A)                                             |
| AGENTS.md 통째 갈아끼우기          | `know-how/AGENTS.md` 만들기 (모드 B)                                  |
| AGENTS.md는 그대로 두고 추가 md 끼우기 | `know-how/EXTRA.md` 만들고 `prefix: [AGENTS.md, know-how/EXTRA.md]` |
| 추가 md를 AGENTS.md보다 먼저 노출    | `prefix:` 리스트에서 순서 바꾸기                                           |

이 메커니즘은 hook의 `.d/` chain과 의도가 같다 — "standard 자원에 내 것을 더하기" — 단지 표현 방식이 자원의 본질에 맞게 다를 뿐.

### 3.3 Standard를 어떻게 "참조"하는가 — symlink와 fork

프로젝트는 `standard/`를 **복사가 아닌 symlink**로 가리킨다.

```
<project>/.harness/standard/AGENTS.md   →  ~/.harness/standard/AGENTS.md
<project>/.harness/standard/hooks       →  ~/.harness/standard/hooks
```

**왜 symlink인가**:
- 글로벌 standard가 갱신되면 모든 프로젝트가 즉시 반영 (share)
- 프로젝트는 standard를 직접 수정할 수 없음 (실수로 글로벌을 깨뜨릴 위험 차단)
- git에 symlink가 자연 commit → "이 프로젝트는 어떤 standard를 참조했나"가 진화 이력에 남음

**프로젝트만 변형하고 싶을 때** — `harness fork <name>`:
- symlink → 로컬 복사로 변환
- 그 후엔 자유 수정, 글로벌 영향 0
- 검증 후 다시 글로벌로 보내고 싶으면 → `harness publish`로 승격

### 3.4 compose.yaml — 결합을 제어하는 SSOT

결합의 결과가 무엇이 될지는 **`<project>/.harness/compose.yaml` 한 파일이 결정**한다. 이게 SSOT(Single Source of Truth).

compose.yaml이 답하는 질문들:

| 질문                     | 키                                       |
| ---------------------- | --------------------------------------- |
| 어떤 모드로 동작?             | `mode: human-gated \| ralph`            |
| LLM prefix에 어떤 md를 주입? | `prefix: [AGENTS.md, ...]`              |
| 어떤 hook을 쓸지            | `hooks.<name>: enabled \| disabled`     |
| Required Context는 무엇?  | `required_context.paths`                |
| 가드레일 임계값은?             | `cognitive_guard.*`, `loop_detection.*` |
| 응답 완료 전 검증할 것은?        | `stop_validation.*`                     |

**핵심**: AGENTS.md는 compose.yaml로부터 **derived**된다. 사용자가 AGENTS.md를 직접 편집하는 게 아니라, compose.yaml만 편집하면 매 세션 새 AGENTS.md가 자동 생성된다. 직접 작성하고 싶을 때만 `know-how/AGENTS.md`를 만들어 override (모드 B).

### 3.5 결합은 언제 일어나나 — `session_start` hook

매 세션 시작 시 `session_start` hook이 발동해 결합을 수행한다.

```
[Claude 세션 시작]
    ↓
session_start hook 실행
    ↓
1. compose.yaml 읽기
2. standard/ + know-how/를 우선순위(3.2의 3 모드)대로 합성
3. 결과를 <project>/.harness/runtime/AGENTS.resolved.md 로 저장
4. 그 파일을 LLM의 system prefix로 주입
    ↓
[작업 시작 — Required Context 강제·trigger 매칭 등 활성]
```

**결합 결과를 직접 보고 싶을 때**:
```bash
cat .harness/runtime/AGENTS.resolved.md
```

이 파일은 자동 생성물이라 수정해도 다음 세션에 덮어써진다. 영구 변경은 compose.yaml 또는 know-how를 거쳐야 함.

### 3.6 결합 흐름 요약 (한 그림)

```
                         [편집 가능한 입력]
                         ─────────────────
~/.harness/standard/        ←─ 글로벌 갱신 (모든 프로젝트 영향)
        │
        │ symlink
        ▼
<project>/.harness/standard/   (수정 X — fork 전까지)
        +
<project>/.harness/know-how/   ←─ 자기 노하우 (override·chain·추가)
        +
<project>/.harness/compose.yaml ←─ SSOT — 결합 정책

                         [세션 시작 시 합성]
                         ───────────────────
                              session_start hook
                                   │
                                   ▼
                         [자동 생성물]
                         ────────────
                  runtime/AGENTS.resolved.md
                              │
                              ▼
                  LLM system prefix로 주입
                              │
                              ▼
                  pre_tool_use hook으로 강제력 발휘
                  (Required·trigger·loop·cognitive)
```

### 3.7 자식이 검증되면 부모로 — `harness publish`

자식 클래스(`know-how/`)에서 만든 게 충분히 검증되면 부모 클래스(`standard/`)로 승격할 수 있다.

```bash
harness publish know-how/skills/my-helper
```

**자격 4 기준** (자세한 내용은 13장):
1. 항상 적용되어야 하는가
2. 압축되면 손해가 큰가
3. 짧게 표현 가능한가
4. 프로젝트 무관 보편적인가

승격되면 `~/.harness/standard/skills/my-helper/`로 이동, 다른 프로젝트는 `harness install skills/my-helper`로 받아 쓸 수 있다. 이 흐름이 **하네스 자체의 진화** 메커니즘 (12 요건 중 11번).

### 3.8 1부 마무리 — 큰 그림

여기까지가 큰 그림이다.

- **1장**: 글로벌 `standard/`는 도구·도메인 무관한 부모 클래스. 모든 프로젝트가 공유하는 검증된 기본값.
- **2장**: 프로젝트 `<project>/.harness/`는 자식 클래스. `compose.yaml`로 정책을 정하고, `know-how/`로 자유 변형.
- **3장 (이번)**: 두 레이어는 매 세션 `session_start` hook이 SSOT(`compose.yaml`)에 따라 합성. 합성 결과(`runtime/AGENTS.resolved.md`)가 LLM의 prefix로 주입되며, hook들이 그 정책을 실제로 강제한다.

다음 2부부터는 그 **강제력의 본체** — AGENTS.md의 4 블록 구조와 5-Hook 시스템을 자세히 본다.

## 2부: 강제력의 본체

## 4. AGENTS.md — 4 블록과 자동 생성

### 4.1 AGENTS.md가 하는 일
> LLM은 매 응답마다 system prefix를 본다. AGENTS.md 본문이 그 prefix에 박혀 세션 동안 **사라지지 않고 유지**되는 텍스트다. 즉 "에이전트가 절대 잊으면 안 되는 것"을 적는 곳.

### 4.2 4 블록 구조

| 블록                    | 의미                           | 예시                                      |
| --------------------- | ---------------------------- | --------------------------------------- |
| **Required Context**  | 시작 시 반드시 읽어야 할 문서 (1~3개로 절제) | `- 프로젝트 정의: docs/.../정의서.md`            |
| **On-Demand Context** | 필요할 때 lazy 읽기                | `- 데이터 명세: docs/.../데이터 명세서.md`         |
| **Trigger → Read**    | 특정 작업 패턴 매칭 시 강제 읽기          | `- DB/스키마 변경 → 데이터 명세 먼저`               |
| **Hard Rules**        | 직접 명시한 강제선 (참조 X)            | `1. Required Context를 읽지 않은 채 코드 변경 금지` |

위 3 블록은 **인덱스/포인터** (참조), 마지막 블록만 **본문 직접 명시**. 이 분리가 다음 절의 압축 정책과 맞물림.

### 4.3 핵심 압축 정책 — 본문 vs 참조

LLM의 system prefix(=AGENTS.md 본문)는 **압축되지 않는다**. 반면 도구 결과(Read로 가져온 문서 본문)는 컨텍스트가 늘면 압축된다.

| 위치 | 압축 |
|---|---|
| AGENTS.md에 **직접 적힌 텍스트** (Hard Rules 등) | ❌ 안 됨 — 세션 끝까지 LLM이 그대로 봄 |
| AGENTS.md가 *path만* 적은 문서 (`- docs/foo.md`) | ✅ 가능 — 도구 결과로 간주 |

따라서 **절대 사라지면 안 되는 룰**은 Hard Rules 블록에 직접 적고, **가끔 참조해도 되는 건** path만 적어 trigger로 lazy load 하는 게 맞다. 4 블록 분리의 근거가 이것.

### 4.4 자동 생성 흐름

```
compose.yaml의 정책
    │ (required_context, on_demand_context, trigger_read, hard_rules)
    ▼
session_start hook
    │ — policy.py가 4 블록 템플릿에 값 채움
    ▼
runtime/AGENTS.resolved.md
    │ — 그 세션의 최종 AGENTS.md
    ▼
LLM의 system prefix로 주입 (provider 어댑터가 처리)
```

사용자가 AGENTS.md를 직접 편집하지 않는 이유: **SSOT가 `compose.yaml`이라서**. AGENTS.md는 derived 결과물이고 매 세션 새로 만들어지므로 직접 수정해도 다음 세션에 덮어써짐.

### 4.5 직접 쓰고 싶을 때 — `know-how/AGENTS.md` override

자동 생성이 아닌 *완전 수작업* AGENTS.md를 쓰고 싶다면 `know-how/AGENTS.md`를 만든다 (3장의 모드 B). 이 파일이 있으면 `session_start` hook이 자동 생성 대신 그것을 그대로 사용.

추가 md를 prefix에 *함께* 박고 싶을 때는 override가 아니라 `compose.yaml`의 `prefix:` 리스트에 추가:

```yaml
prefix:
  - AGENTS.md
  - know-how/COMPANY-RULES.md
```

→ 두 파일이 위→아래 순서로 LLM prefix에 누적 (3.2 절의 MD 영역 chain).

### 4.6 다음 — 강제력은 누가 발휘하나

지금까지는 "어떤 텍스트가 LLM 앞에 놓이는가"의 이야기. 하지만 텍스트만으로는 강제가 안 된다 — LLM은 prompt를 무시하고 행동할 수 있다. Required Context 미읽음을 실제로 *차단*하는 건 다음 5장의 hook 시스템.

## 5. 5-Hook 시스템 (Claude 이벤트 매핑)

> 참조: [claude hook 시스템 레퍼런스](claude-hook-reference.md) — Claude Code의 hook 이벤트·envelope·exit code 규약을 자세히 정리한 외부 레퍼런스 문서.

### 5.1 Hook이 강제력의 본체인 이유

Claude는 prompt 텍스트(AGENTS.md 본문)를 *권고*로 받는다. 무시하고 행동할 수 있다. 반면 hook은 도구 실행 직전 시스템이 가로채는 지점이라 **물리적으로 막을 수 있다**. 그래서 "Required 미읽으면 Edit 차단" 같은 강제력은 prompt가 아닌 hook이 발휘.

### 5.2 5 Hook ↔ Claude 이벤트 1:1 매핑

| Hook 파일 | Claude 이벤트 | 책임 | 실패 시 |
|---|---|---|---|
| `session_start.sh` | `SessionStart` | resolved.md 생성 → prefix 주입 → status 초기화 | 사용자 안내 |
| `user_prompt_submit.sh` | `UserPromptSubmit` | input filter, prompts.jsonl 기록, placeholder 가드 | 통과/거부 |
| `pre_tool_use.sh` | `PreToolUse` | Required·trigger·loop·cognitive 검사 | **차단** (보수적) |
| `post_tool_use.sh` | `PostToolUse` | status 갱신, trace append, timing diff | 통과 (로그) |
| `stop.sh` | `Stop` | AGENTS.md 4 블록 검증, `stop_validation.checks` 실행 | warn 또는 block |

`+post_commit.sh` (git post-commit)도 있어서 진화 CHANGELOG를 자동 갱신함 — Claude 이벤트는 아니고 git 이벤트.

### 5.3 우선순위 — standard / know-how / chain

3장에서 다룬 OOP 결합 모델이 hook에도 그대로 적용:

```
1. know-how/hooks/<name>.sh 있음   → standard 무시, 통째 override (모드 B)
2. .sh 없고 <name>.d/ 있음          → standard 실행 후 .d/ chain (모드 C, 알파벳 순)
3. 둘 다 없음                        → standard 그대로 (모드 A)
```

### 5.4 강제력 메커니즘 — exit code 프로토콜

Hook은 stdin으로 envelope JSON을 받고, **종료 코드와 stderr로 결정 전달**:

| exit | stdout/stderr | 의미 |
|---|---|---|
| `0` | (없음) | **allow** — 그대로 진행 |
| `2` | stderr에 메시지 | **self_correct** — 차단 + claude가 stderr 읽고 자가수정 |
| `1` | stdout `{"continue": false}` JSON | **hard_stop** — 즉시 정지 (turn 끝) |

Required Context의 severity도 이 두 단계에 매핑됨 (`self_correct` vs `hard_stop`).

> **왜 exit 2를 1차로 골랐나, JSON 출력은 언제 쓰나** → [claude hook 시스템 레퍼런스 §5](claude hook 시스템 레퍼런스#5. 왜 exit 2를 메인으로 골랐나.md)


### 5.5 실제로 무엇이 차단되나 (예시 3)

`pre_tool_use`가 검사하는 게이트들:

- **Required Context 미읽음** → Edit/Write 시도 시 `runtime/sessions/<id>/required-status.json`에 unread 있으면 deny
- **Trigger → Read 매칭** → Edit하려는 path가 `**/*.sql` 등 매칭되면 require 문서 미읽었을 때 deny
- **Cognitive guard 초과** → 한 번에 200줄 넘게 변경 시도 시 deny (bypass marker로 1회 통과)
- **Doom loop** → 같은 path 연속 3회 수정 시 deny

각 deny는 `decisions.jsonl`에 카테고리·이유와 함께 기록 → 12장 improve가 분석.

## 6. 기본 Persona — 범위 제한으로 더 안전한 응답

Persona는 *"이 에이전트는 무엇을 하는 누구인가"* 를 미리 정해두는 것. 단순한 정의 한 줄이지만 효과는 크다 — LLM의 응답 범위가 좁혀지고, 의도 외 영역으로 일탈하지 않음. 입문에서는 *기본 정의*만 잡고 가는 안정성을 다루고, 적극 활용(역할 분담·라우팅·multi-persona)은 [My Harness System — 중급](02-중급.md)에서 본다.

### 6.1 왜 Persona가 안전 axis인가

Persona는 보통 *성능 향상*(포커스↑) 도구로 알려져 있지만, 입문 frame에선 **안전**의 한 면이 더 중요하다.

| 면 | 효과 |
|---|---|
| 성능 | 산만함을 줄여 응답 품질↑ |
| **안전 (입문 frame)** | "이 에이전트는 백엔드 개발자만"·"테스트 작성자만" 같은 *범위 제한* → 의도 외 행동 방지 |

5장의 5-Hook이 *"뭐는 하지마"*의 양적 제한이라면, Persona는 *"누가 무엇을 하는가"*의 질적 제한. 같은 Karpathy 한정 철학의 다른 면이다.

### 6.2 Persona는 어디 적나 — AGENTS.md의 한 블록

특별한 새 메커니즘은 없다. **AGENTS.md 본문에 직접** 쓰면 끝. compose.yaml의 `prefix:` 리스트로 주입되는 표준 md에 한 블록 추가:

```markdown
# AGENTS.md

## Persona
당신은 이 프로젝트의 **백엔드 개발자**입니다.
- 책임 영역: API 서버, 데이터베이스, 도메인 로직
- 다루지 않는 영역: 프론트엔드 UI, 디자인, 마케팅 카피

## Required Context
...
```

또는 별도 md로 분리:

```yaml
# compose.yaml
prefix:
  - AGENTS.md
  - know-how/PERSONA.md       # 별도 페르소나 정의 파일
```

`know-how/PERSONA.md`에 페르소나 본문을 따로 두면, 프로젝트마다 다른 페르소나를 두고 같은 AGENTS.md를 공유할 수 있다.

### 6.3 좋은 Persona의 3 요소

입문 단계에서는 다음 3 요소만 짧게 적어도 충분:

| 요소 | 예시 |
|---|---|
| **역할** | 백엔드 개발자 / SRE / 테스트 작성자 / 문서 정리 보조 |
| **책임 영역** | API 서버, DB 스키마 / 빌드 스크립트, CI/CD / 단위·통합 테스트 |
| **다루지 않는 영역** | 프론트엔드 UI / 비즈니스 로직 변경 / production 배포 |

특히 *다루지 않는 영역*이 **안전 측면의 핵심**. 명시 안 하면 LLM이 "도와준다"며 의도 외 영역까지 손댐.

### 6.4 압축 정책 — Persona도 prefix에 직접

4.3 절에서 본 것처럼 **AGENTS.md 본문에 직접 적힌 텍스트는 압축되지 않는다**. Persona는 세션 끝까지 LLM이 *항상* 보고 있어야 효과가 있으므로 무조건 본문 직접 명시. 다른 문서를 참조(`- docs/persona.md`)만 하면 압축돼 사라질 위험.

### 6.5 다음 — 가드레일

5장의 강제력 + 6장의 Persona가 *"무엇을 알고 누구로서 일할지"*를 정한다. 다음 3부는 거기에 더해 *"행동 자체에 거는 한계"* — 한 번에 너무 큰 변경을 막고(cognitive guard), 같은 자리 맴돌기를 잡고(doom loop), 응답 끝내기 전 검증(stop validation)을 본다.

## 3부: 가드레일

> **잠깐 — Hook이랑 가드레일이 뭐가 다른가?**
> Hook은 *메커니즘* (어디에 끼어드는 장치), 가드레일은 *정책* (그 장치로 만든 행동 제한). 모든 가드레일은 hook으로 구현되지만, 모든 hook이 가드레일은 아님 (post_tool_use의 단순 추적, session_start의 컨텍스트 주입은 가드레일이 아님).
>
> 차단의 **대상**으로 둘을 가르면:
> - **2부 (4·5장) 컨텍스트 강제** — *무엇을* 알고 있어야 하는가 (Required·Trigger)
> - **3부 (7·8장) 행동 가드레일** — *얼마나/어떻게* 행동해야 하는가 (큰 변경·반복·검증)
>
> 둘 다 `pre_tool_use` hook이 검사하지만, 의도는 다름 — *정보 결핍* 방지 vs *행동 폭주* 방지.

## 7. Cognitive Guard + Doom Loop 감지

LLM은 한 번에 너무 많이 바꾸거나 같은 자리를 의미 없이 맴돌 수 있다. 사람이 옆에서 *"잠깐, 너무 큰데?"* / *"같은 거 또 고치는 거 아니야?"* 라고 멈출 일을 시스템이 자동으로 한다.

### 7.1 Cognitive Guard — 한 번에 너무 큰 변경 차단

LLM의 인지 한계를 보완. 실수로 200줄짜리 diff를 한 번에 만들거나 한 세션에 1000줄 넘게 쌓이는 걸 막음.

```yaml
cognitive_guard:
  per_call:    { max_diff_lines: 200, max_new_files: 3 }
  per_session: { max_changed_files: 10, max_diff_lines: 1000 }
  on_breach: ask_human               # ralph 모드에선 abort fallback
  bypass_marker: "@harness allow-large"
```

- **per_call**: 한 도구 호출의 diff 크기 (Edit/Write 한 번)
- **per_session**: 세션 누적 (`runtime/sessions/<id>/cognitive-guard.json`에 기록)

### 7.2 Bypass Marker — 진짜 큰 변경이 필요할 때

리팩토링이나 마이그레이션처럼 의도적으로 큰 변경을 해야 하는 상황. prompt에 마커를 넣으면 한 번 통과:

```
@harness allow-large

이 큰 마이그레이션 적용해줘 ...
```

`user_prompt_submit` hook이 마커를 감지해 status에 기록 → `pre_tool_use`가 그 세션에서 한 번만 cognitive guard skip.

### 7.3 Doom Loop — 같은 path 반복 수정 차단

LLM이 같은 파일을 의미 없이 계속 고치는 패턴. 보통 *원인을 못 찾고 증상만 만지는* 신호.

```yaml
loop_detection:
  consecutive_same_path: 3
  on_loop: self_correct               # | hard_stop
```

`post_tool_use`가 `cognitive-guard.json`의 `edit_history`에 path를 누적, `pre_tool_use`가 마지막 N개가 모두 같은 path면 deny. Bypass marker로 우회 가능.

### 7.4 동작 흐름

```
[LLM이 Edit("src/foo.ts", ...) 호출]
        ↓
pre_tool_use hook
        ├─ cognitive guard: diff 라인 수 추정 → 임계값 비교
        ├─ doom loop: edit_history 마지막 N개가 같은 path인가
        └─ 모두 통과 → allow
        
[deny 시] → exit 2 + stderr ("큰 변경 감지: 250 > 200")
        ↓
LLM이 stderr 보고 → 더 작게 쪼개서 재시도 또는 "@harness allow-large" 요청
```

### 7.5 다음 — 응답 완료 직전 검증

위 가드레일은 *도구 호출 직전*에 작동. 8장의 Stop Validation은 *응답 완료 직전* — "검증 안 거친 응답을 사용자에게 내보내지 않게" 하는 마지막 가드.

## 8. Stop Validation

7장이 *도구 호출 직전*의 가드라면, 8장은 *응답 완료 직전*의 가드. LLM이 "끝났어요" 하기 전에 마지막으로 검증을 돌려, 통과 못 하면 **응답을 못 끝내게** 막거나 경고를 붙임. `stop` hook이 이 역할을 수행.

### 8.1 언제·왜 필요한가

가장 흔한 시나리오는 **테스트·타입체크·린트 미통과 채로 응답을 끝내는** 경우. LLM이 작업을 완료했다고 선언했지만 사실 빌드가 깨져있는 상황을 자동으로 잡음. 도구 호출 가드(7장)는 *미리* 막는 거고, stop validation은 *마지막에* 잡는 거라 성격이 다름.

### 8.2 설정

```yaml
stop_validation:
  enabled: false                    # 처음엔 꺼두고 필요 시 활성화
  on_fail: warn                     # warn (경고만) | block (응답 차단)
  checks:
    - { command: "pytest -x" }
    - { command: "tsc --noEmit" }
    - { script: ./know-how/checks/no-todo.sh }
```

- `command`: 임의 셸 명령
- `script`: 프로젝트 안의 실행 가능 스크립트 path

각 check가 exit 0이면 통과, non-zero면 실패. 실패 메시지(stdout/stderr 일부)는 결과에 포함됨.

### 8.3 on_fail — warn vs block

| 정책 | 실패 시 동작 | 언제 쓰나 |
|---|---|---|
| **warn** | 응답은 그대로 끝나되 경고 메시지가 추가 | 가벼운 체크 (예: TODO 탐지). 사람이 인지만 하면 충분 |
| **block** | 응답 종료를 막음 (`exit 2 + stderr`) → LLM이 메시지 보고 재시도 | 진짜 중요한 게이트 (예: 테스트 깨짐). 검증 통과까진 끝내면 안 됨 |

`block`은 5장의 self_correct와 동일 메커니즘 — stderr를 LLM이 받아 재작업.

### 8.4 비용 트레이드오프

`stop_validation`은 **매 응답마다 실행**됨. 그래서:

- `pytest -x` 같은 풀 테스트를 매번 돌리면 응답마다 수십 초 추가
- 빠른 게이트(`tsc --noEmit`, lint, 간단한 grep)만 두는 게 현실적
- 무거운 검증은 CI에 맡기고 stop validation은 *얕은* 검증으로 (무인 루프(Ralph)는 [My Harness System — 중급](02-중급.md) 참조)

처음엔 `enabled: false`로 두고, 정말 매 응답에 강제하고 싶은 게 생겼을 때만 활성화하는 흐름이 안전.

### 8.5 다음 — 시작하기 (4부)

## 9. CLI 입문 명령

입문 단계에서 자주 쓸 5 명령. 이 정도만 알면 단일 에이전트 운영 가능.

### 9.1 `harness init` — 프로젝트에 하네스 끼우기

```bash
cd <my-project>
harness init
```

생성되는 것:
- `<project>/.harness/compose.yaml` — SSOT (이 한 파일만 편집하면 동작 다 바뀜)
- `<project>/.harness/standard/` — 글로벌 standard로의 symlink
- `<project>/.harness/know-how/` — 빈 폴더 (자기 노하우 자유 추가)
- `<project>/.harness/runtime/` — 자동 생성될 곳 (gitignore)
- git post-commit hook 설치 (변경 이력 자동 추적)

### 9.2 `harness link claude` — provider 연결

```bash
harness link claude
```

`<project>/.claude/settings.local.json`에 5 hook을 자동 등록. 새 claude 세션부터 hook이 활성화됨. 글로벌 `~/.claude/settings.json`은 건드리지 않음 — 다른 프로젝트에 영향 0.

해제는 `harness unlink claude`.

### 9.3 `harness reload` — compose.yaml 변경 후 즉시 반영

compose.yaml을 직접 편집하고 *다음 세션을 기다리지 않고* 지금 적용하고 싶을 때:

```bash
harness reload
```

`runtime/AGENTS.resolved.md`를 즉시 재생성. 이미 진행 중인 세션은 다음 hook 호출부터 새 정책 반영.

### 9.4 `harness doctor` — 환경 진단

뭔가 안 동작할 때 가장 먼저:

```bash
harness doctor
```

체크 항목:
- `~/.harness/` 글로벌 standard가 있는가
- `<project>/.harness/`가 init돼 있는가
- provider 등록 상태 (`.claude/settings.local.json`에 hook 등록됐는지)
- compose.yaml 파싱 가능 여부
- 5 hook 스크립트 존재·실행 권한

문제가 있으면 *어디가 깨졌는지* 한 줄로 알려줌.

### 9.5 `harness version` — 버전 확인

```bash
harness version
```

- 하네스 버전
- 활성 plugin 목록
- 연결된 provider

### 9.6 자주 쓰는 흐름

```bash
# [최초 1회]
cd my-project
harness init
harness link claude
# compose.yaml의 required_context.paths를 자기 프로젝트 path로 채우기
$EDITOR .harness/compose.yaml

# [세션 시작]
claude        # 새 claude 세션. AGENTS.md가 자동 주입됨.

# [정책 변경]
$EDITOR .harness/compose.yaml
harness reload         # 즉시 적용
# 또는 새 세션 시작

# [문제 발생]
harness doctor         # 진단
```

## 10. Provider 어댑터 — Claude 통합

5 hook은 *표준 envelope*(우리가 정한 JSON)을 기준으로 동작한다. Claude Code는 자기만의 envelope·등록 방식이 있어서, 그 차이를 흡수하는 게 *어댑터*. 입문에서는 Claude만 다룬다 (codex / 다른 provider는 [My Harness System — 중급](02-중급.md)).

### 10.1 어댑터가 하는 일

```
Claude Code의 PreToolUse JSON  →  translate-pre.sh  →  표준 envelope  →  pre_tool_use.sh (표준 hook)

표준 hook의 exit 2 + stderr  →  Claude가 그대로 인식 → LLM에 자가수정 메시지 전달
```

`translate-*.sh`가 jq로 JSON 변환을 처리. 사용자가 직접 만질 일은 없음 — `harness link claude`가 자동으로 등록.

### 10.2 등록 위치 — `<project>/.claude/settings.local.json`

```json
{
  "hooks": {
    "SessionStart":      [{"hooks": [{"type": "command", "command": "~/.harness/standard/adapters/claude/translate-start.sh"}]}],
    "UserPromptSubmit":  [{"hooks": [{"type": "command", "command": "~/.harness/standard/adapters/claude/translate-prompt.sh"}]}],
    "PreToolUse":        [{"matcher": "Edit|Write|NotebookEdit|Bash", "hooks": [...]}],
    "PostToolUse":       [...],
    "Stop":              [...]
  }
}
```

**왜 글로벌이 아닌 프로젝트 로컬?**: 글로벌 `~/.claude/settings.json`을 건드리면 다른 프로젝트에 의도치 않게 영향. 프로젝트 로컬 `settings.local.json`은 git ignore 가능 + 격리 보장.

### 10.3 도구 중립 invariant

표준 envelope·표준 hook은 **provider 무관하게 안정**. claude를 codex로 바꾸려면 `harness link codex` 한 줄. AGENTS.md / compose.yaml / 가드레일 / Persona 모두 그대로 동작.

이 invariant 덕분에 입문에서 배운 *모든 정책·가드레일*이 다른 도구로 옮겨도 그대로 살아남음.

## 11. 입문을 통달했다면

이 입문서를 끝까지 읽고 한 프로젝트에서 실제로 운영해봤다면, 단일 에이전트의 *방어 메커니즘*은 모두 갖춘 셈이다. 다음 단계는 **확장**.

### 11.1 더 빠르게, 더 많이 위임 → [My Harness System — 중급](02-중급.md)

- **Subagent 위임** — 한 에이전트가 모든 일을 다 하지 말고 분할
- **Worktree 병렬** — 여러 작업을 동시에
- **세션 공유** — 어제 세션의 맥락을 오늘 세션이 이어받음
- **컨텍스트 관리 고급** — prefix 동적 조정, 압축 정책 적극 활용
- **Persona 적극 활용** — 역할 분담, 라우팅, multi-persona orchestration
- **Multi-agent ensemble** — 여러 모델을 조합해 품질 향상
- **Ralph 무인 루프** — 사람 없이 task만 주고 떠나기
- **6 viz 렌더러 + Dashboard** — 흐름·병목·개선 제안 시각화
- **Eval / Improve / LLM-as-judge** — 측정·자동 개선·정성 평가
- **진화 추적 (CHANGELOG / Snapshot / Publish)** — 하네스 자체의 진화

### 11.2 Trade-off를 직접 조절하고 싶을 때 → [My Harness System — 고급](03-고급.md)

입문·중급의 도구를 모두 익히고 나면, 다음 질문이 자연스럽게 떠오른다:
- *"가드레일을 너무 빡빡하게 걸면 작업이 느려지고, 너무 풀면 폭주한다. 어디서 균형을 잡지?"*
- *"이 프로젝트엔 어떤 hook을 끄고, 어떤 임계값을 올릴까?"*
- *"여러 사람·에이전트가 같은 프로젝트를 운영할 때 어떤 정책을 통일하고 어떤 걸 분기시킬까?"*

이 trade-off 판단력 자체가 [My Harness System — 고급](03-고급.md)의 콘텐츠.

### 11.3 마무리 — 입문서가 끝나는 지점

> *"내 인지 한계를 넘는 일은 LLM에게도 시키지 않는다."*

이 한 줄이 입문서의 본질. Hook으로 의도 외 행동을 차단하고, 가드레일로 인지 한계를 보호하고, Persona로 범위를 좁힌다 — 사람과 LLM이 같은 속도로 갈 수 있게.

여기까지를 자신의 프로젝트에서 *직접 운영*해본 사람만이 다음 단계인 *확장*과 *trade-off 조절*에서 의미 있는 결정을 할 수 있다. 천천히, 한 단계씩.
