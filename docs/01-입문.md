## 1부: 큰 그림

## 1. standard 와 know-how — 두 축

하네스의 첫 번째 결정: **검증된 기본 구성**과 **내 자산**을 물리적으로 분리한다.

|  | standard | know-how |
|---|---|---|
| **무엇** | 도구/도메인 중립의 검증된 기본 구성 | 실험적 시도 또는 프로젝트 성격이 묻어나는 자산 |
| **누구 것** | 모든 프로젝트가 공유 (검증된 합의는 시간 따라 쌓임) | 내 프로젝트만의 것 |
| **수정** | 글로벌 `~/.harness/standard/` 는 손대지 않음 | 자유 편집 |
| **충돌** | 같은 id 가 양쪽에 있으면 에러 — override 원하면 다른 id 로 |

`know-how/` 의 무언가가 충분히 검증되어 누구에게나 도움이 되면 `standard/` 로 **승격** 가능 (publish 흐름). 이것이 시스템 자체의 진화 메커니즘.

### 1.1 폴더 구조 — 글로벌 + 프로젝트

두 단위가 있다:

- **글로벌** `~/.harness/` — 한 번 깔린다. `git clone https://github.com/Jungjihyuk/lantern_harness && ./install.sh` 로 설치.
- **프로젝트** `<project>/.harness/` — 프로젝트마다 생긴다. `harness init` 으로 생성.

```
~/.harness/                          글로벌 (한 번 설치)
├── standard/                        검증된 기본 구성 (7 메커니즘 폴더)
│   └── roles.yaml                   5 도메인별 허용 role 목록 (검증 기준)
├── know-how/                        글로벌 사용자 know-how (보통 비어있음 — 프로젝트별이 일반)
├── lib/                             파이썬 모듈 (compose 파서·resolver·validator·adapter 엔진 등)
├── bin/                             CLI (harness 엔트리 + 서브명령)
└── registry.yaml                    카탈로그 (UI 검색용)


<project>/.harness/                  프로젝트 단위 (harness init 으로 생성)
├── compose.yaml                     SSOT — "무엇을 어떤 역할로 활성화할지"
├── know-how/                        내 프로젝트만의 자산 (standard 와 같은 7 메커니즘 구조)
├── runtime/                         자동 생성 (gitignore 권장)
│   ├── AGENTS.resolved.md           session_start 가 매 세션 만드는 LLM prefix
│   ├── traces/<session-id>.jsonl    도구 호출 등 관측 이벤트
│   └── sessions/<session-id>/...    status, decisions, prompts 등
└── evolution/                       git tracked — 진화 이력 (옵션)
```

## 2. artifact — 시스템의 최소 단위

모든 자원은 같은 패턴의 폴더로 존재한다:

```
<mechanism>/<id>/
├── manifest.yaml          이 자원이 무엇인지 / 어디에 등록되는지
└── <entry>                실제 본문 또는 코드 (.md / .sh / .py / .yaml 등)
```

예시 — 시스템 prefix 텍스트 artifact:

```yaml
# standard/instructions/agents_md/manifest.yaml
id: agents_md
domain: cognition
mechanism: instructions
purpose: harness 시스템 prefix 텍스트 (정체성 + 행동 원칙)
roles: [prefix_injection]
entry: ./AGENTS.md
```

**핵심 필드:**

| 필드 | 의미 |
|---|---|
| `id` | 시스템 전체에서 unique. `compose.yaml` 에서 이 id 로 활성화 |
| `mechanism` | 어느 폴더에 속하는가 (instructions / hooks / tools / adapters / workflows / traces / evals) |
| `domain` | 어느 역할 영역인가 (cognition / state / action / guard / observe) |
| `roles` | 이 artifact 가 수행하는 역할 목록 — 도메인에 허용된 role enum 만 가능 (목록은 `standard/roles.yaml` 에 정의) |
| `entry` | 실제 본문 / 실행 entry 의 경로 |

> **원칙**: 자원 하나를 추가/이동/삭제할 때 polder 한 단위만 다루면 끝. `id` 가 변하지 않는 한 `compose.yaml` 안에서 안정.

## 3. 7 메커니즘 — 폴더가 곧 분류

`standard/` 와 `know-how/` 둘 다 같은 7 폴더 구조 (mirror).

| 폴더 | 의미 | 대표 자원 |
|---|---|---|
| `instructions/` | LLM 이 prefix 로 읽는 텍스트 | AGENTS.md, persona, rules |
| `hooks/` | provider 이벤트 시점에 실행되는 코드 | session_start, pre_tool_use 등 |
| `tools/` | LLM 이 직접 행사 못 하는 능력의 로컬 실행 스크립트 | (도메인별로 추가) |
| `adapters/` | 외부 시스템 (provider, protocol) 과의 결합 표면 | claude, codex |
| `workflows/` | 자가 구동 반복 루프 | ralph |
| `traces/` | input/output·토큰·에러 등 raw 관측 데이터 정의 | (수집 정의) |
| `evals/` | 성공 기준·검증 verdict | 회귀 테스트 케이스 |

이건 **수평 분류** — "이 자원이 어디 사는가". 각 폴더 안의 자원은 모두 `<id>/manifest.yaml + entry` 패턴을 따른다.

> 새 자원을 만들 때 가장 먼저 던지는 질문: *"이건 어느 폴더에 들어가야 자연스러운가?"* — 텍스트인가, 코드인가, 외부 결합인가, 자가 루프인가, 관측인가, 검증인가.

## 4. compose.yaml — 활성화 지도

`compose.yaml` 한 파일이 *"내 프로젝트에서 어떤 자원이 어떤 역할로 활성화되어 있는가"* 의 답. SSOT (Single Source of Truth).

7 메커니즘이 "어디에 사는가" 라면, compose.yaml 은 자원을 **역할 영역(도메인)** 별로 정리한다.

| 도메인 | 의미 |
|---|---|
| **cognition** | LLM 의 인지 — prefix 텍스트, context 강제, persona, rules |
| **state** | 세션·상태 관리 — status 추적, workflow, memory |
| **action** | 외부 호출 — provider adapter, tools |
| **guard** | 가드레일 — required check, cognitive guard, loop detection, stop validation |
| **observe** | 관측·평가 — trace 기록, metric 수집, eval verdict |

예시:

```yaml
# <project>/.harness/compose.yaml
version: 2

cognition:
  instructions:
    - agents_md                                 # id 만 — 기본 role 사용
  context:
    required:
      - {id: project_readme, src_path: README.md, label: 프로젝트 개요}
    triggered: []
    suggested: []
  rules: []
  hooks:
    - {id: session_start, role: prefix_injection}
    - {id: pre_tool_use, role: context_gating}

state:
  hooks:
    - {id: session_start, role: status_init}
    - {id: post_tool_use, role: status_track}

action:
  adapters:
    - claude_adapter

guard:
  hooks:
    - {id: pre_tool_use, role: required_check}
    - {id: pre_tool_use, role: cognitive_guard}
    - {id: pre_tool_use, role: loop_detection}
    - {id: stop, role: stop_validation}
  policies:
    cognitive_guard:
      per_call: {max_diff_lines: 200, max_new_files: 3}
      per_session: {max_changed_files: 10, max_diff_lines: 1000}
      on_breach: ask_human

observe:
  hooks:
    - {id: post_tool_use, role: trace_log}
    - {id: post_tool_use, role: metric_collect}
```

### N:N 매핑이 정직하게 표현된다

`pre_tool_use` 라는 한 hook artifact 가 위 예시에서 **세 도메인** 에 다른 role 로 등장:

- `cognition.hooks` → `context_gating` (context 강제)
- `guard.hooks` → `required_check` + `cognitive_guard` + `loop_detection` (가드)

한 자원이 여러 역할을 동시에 수행하는 것이 정직히 표현된다. 자원의 **본질** (hook 인 것) 과 **역할** (어느 도메인에서 무엇을 하는지) 이 분리됨.

### compose 만 편집하면 끝

AGENTS.md / hook 활성화 / 가드레일 임계값 / required context 등 모든 정책이 여기에. `compose.yaml` 만 편집하면 매 세션부터 새 정책이 적용된다.

## 5. 결합 — 매 세션 시작 시

`harness init` 으로 프로젝트에 `.harness/` 가 만들어지고, `harness link claude` (또는 `link codex`) 로 provider 의 hook 시스템에 등록되면 — 그 후로는 매 세션마다 자동 흐름:

```
[provider 가 세션 시작]
       ↓
session_start hook 발동
       ↓
1. compose.yaml 읽기
2. standard + know-how 의 artifact 들을 id 로 resolve
3. cognition 의 instructions·context·rules 를 모아 AGENTS.md 생성
4. AGENTS.md 를 LLM system prefix 로 주입 (provider adapter 가 처리)
       ↓
[작업 시작]
       ↓
도구 호출 직전 pre_tool_use hook 이 가드 정책 강제
(required_check / cognitive_guard / loop_detection / context_gating)
       ↓
도구 호출 후 post_tool_use hook 이 status·trace·metric 갱신
       ↓
[응답 종료 직전]
       ↓
stop hook 의 stop_validation 검증
```

**결합 결과를 직접 보고 싶을 때:**
```bash
cat .harness/runtime/AGENTS.resolved.md
```

이 파일은 자동 생성물이라 직접 수정하면 다음 세션에 덮어써진다. 영구 변경은 `compose.yaml` 또는 `know-how/` 를 통해.

### 1부 마무리

| 핵심 개념 | 한 줄 |
|---|---|
| **standard** | 도구/도메인 중립 검증된 기본 구성 (글로벌 + 프로젝트의 발견 대상) |
| **know-how** | 내 프로젝트만의 자산 (실험적 또는 프로젝트 성격) |
| **artifact** | `<mechanism>/<id>/manifest.yaml + entry` — 최소 단위 |
| **7 메커니즘** | 자원이 사는 폴더 (instructions / hooks / tools / adapters / workflows / traces / evals) |
| **5 도메인** | 자원의 역할 영역 (cognition / state / action / guard / observe — `compose.yaml` 의 최상위 키) |
| **N:N 매핑** | 한 자원이 여러 도메인에 다른 role 로 등장 가능 — 정직히 표현됨 |
| **compose.yaml** | "무엇이 어떤 역할로 활성화되었는가" 의 SSOT |
| **결합** | 매 세션 `session_start` 가 compose 읽고 AGENTS.md 자동 생성, hook 들이 정책 강제 |

다음 2부부터는 그 **강제력의 본체** — AGENTS.md 자동 생성 흐름과 hook 시스템이 어떻게 정책을 강제하는지 자세히 본다.

## 2부: 바로 활용

이제 시스템을 *실제로 돌려보자*. 가장 흔한 흐름은: 설치 → 프로젝트 초기화 → provider 연결 → 첫 세션 → compose 한두 줄 편집.

## 6. 설치와 초기화

### 6.1 글로벌 설치 — 한 번만

```bash
git clone https://github.com/Jungjihyuk/lantern_harness
cd lantern_harness
./install.sh
```

이걸 한 번 실행하면 `~/.harness/` 가 만들어진다 (`standard/` · `lib/` · `bin/` · `know-how/` · `registry.yaml`). 모든 프로젝트가 이 글로벌 자원을 공유한다.

이후 `harness` 명령을 어디서나 쓸 수 있게 셸 설정 한 줄:

```bash
export PATH="$HOME/.harness/bin:$PATH"
```

확인:
```bash
harness version
```

### 6.2 프로젝트 초기화

내 프로젝트 폴더에서:

```bash
cd <my-project>
harness init
```

만들어지는 것:

```
<my-project>/.harness/
├── compose.yaml          ← 편집할 단 하나의 파일 (SSOT)
├── know-how/             ← 내 프로젝트만의 자산 (빈 상태로 시작)
├── runtime/              ← 자동 생성될 곳 (gitignore 권장)
└── README.md             ← 짧은 안내
```

기본 `compose.yaml` 은 합리적 기본값으로 채워져 있다 — 가드레일 정책 + 핵심 hook 활성화.

### 6.3 provider 연결

```bash
harness link claude
```

`<my-project>/.claude/settings.local.json` 에 hook 들이 자동 등록된다. 글로벌 `~/.claude/settings.json` 은 건드리지 않음 — 다른 프로젝트에 영향 0.

(Codex 사용 시: `harness link codex`)

해제: `harness unlink claude`

### 6.4 무엇이 생겼는지 확인

```bash
harness list           # 글로벌 + 프로젝트의 자산 목록
harness validate       # compose.yaml + manifests + roles 일관성 검증
harness doctor         # 환경 진단 (뭔가 안 동작할 때 첫 명령)
```

이 세 명령이면 *"내 시스템에 뭐가 있고 잘 깔렸는지"* 가 한눈에 보인다.

## 7. 첫 세션 — 무엇이 어떻게 작동하는가

`harness init` + `harness link claude` 가 끝났으면, 그 프로젝트에서 새 Claude 세션을 시작하면 자동으로 시스템이 발동한다.

### 7.1 세션 시작 흐름

```
[Claude 세션 시작]
       ↓
session_start hook 발동
       ↓
1. compose.yaml 읽기
2. cognition 도메인의 instructions / context / rules 합성
3. runtime/AGENTS.resolved.md 생성
4. 그 내용이 LLM system prefix 로 주입
       ↓
[작업 시작 — 모든 도구 호출이 hook 들을 거침]
```

### 7.2 LLM 이 무엇을 보는지 확인

```bash
cat .harness/runtime/AGENTS.resolved.md
```

이 파일이 그 세션 동안 LLM 의 system prefix 에 박힌 텍스트. 직접 수정하면 다음 세션에 덮어써짐 (자동 생성물). 영구 변경은 `compose.yaml` 을 통해.

### 7.3 도구 호출 시

LLM 이 Edit / Write / Bash 같은 도구를 부르려 하면:

```
[LLM: Edit("src/foo.ts", ...)]
       ↓
pre_tool_use hook 실행
       ├─ required_check    : Required Context 다 읽었나?
       ├─ cognitive_guard   : 한 번에 너무 큰 diff 아닌가?
       ├─ loop_detection    : 같은 path 반복 수정 아닌가?
       └─ → allow / self_correct / hard_stop
       ↓
[allow 시 도구 실행 → 결과 LLM 으로]
       ↓
post_tool_use hook (status·trace·metric 갱신)
```

각 hook 의 결정은 `runtime/sessions/<id>/decisions.jsonl` 에 기록.

### 7.4 세션 끝 — 남은 흔적

응답 종료 직전 `stop` hook 이 `stop_validation` 정책을 검증 (예: 테스트 통과 여부). 정책에 따라 응답 허용 또는 차단.

세션이 닫히면 `<my-project>/.harness/runtime/sessions/<session-id>/` 에 다음이 남는다:

- `decisions.jsonl` — 각 hook 의 결정 (allow/deny + 이유)
- `traces/<session-id>.jsonl` — 도구 호출·이벤트 raw 기록
- `meta.json` — 시작 시각, transcript path 등

이 데이터가 나중에 *"내 시스템이 어떻게 동작했나"* 의 분석 근거가 된다.

## 8. compose.yaml 편집 — 4 시나리오

`compose.yaml` 한 파일만 편집하면 시스템 동작이 바뀐다. 가장 흔한 4가지.

### 8.1 시나리오 A — prefix 텍스트 추가

내 프로젝트에 *"항상 LLM 이 알고 있어야 할 텍스트"* 를 추가하고 싶을 때.

**1단계** — know-how 에 instructions artifact 만들기:

```
<my-project>/.harness/know-how/instructions/company_rules/
├── manifest.yaml
└── COMPANY_RULES.md
```

`manifest.yaml`:
```yaml
id: company_rules
domain: cognition
mechanism: instructions
purpose: "회사 공통 규약"
roles: [prefix_injection]
entry: ./COMPANY_RULES.md
```

`COMPANY_RULES.md`:
```markdown
## Company Rules

- 외부 API 호출은 src/integrations/ 하위에서만.
- DB 마이그레이션은 사용자 승인 후 실행.
```

**2단계** — `compose.yaml` 에 활성화:

```yaml
cognition:
  instructions:
    - agents_md
    - company_rules     # ← 추가
```

**3단계** — 다음 세션을 기다리거나 `harness reload`. `cat .harness/runtime/AGENTS.resolved.md` 로 본문 확인.

### 8.2 시나리오 B — Required Context 한 개 설정

*"이 프로젝트에서 작업 시작 전 LLM 이 반드시 읽어야 하는 문서"* 를 강제하고 싶을 때.

```yaml
cognition:
  context:
    required:
      - {id: project_readme, src_path: README.md, label: 프로젝트 개요}
```

다음 세션부터 LLM 이 `README.md` 를 안 읽은 채 Edit/Write 를 시도하면 차단된다 (pre_tool_use 의 `required_check` role).

> 너무 많이 적지 말 것. 1~3개가 좋은 기준. 작업 시작 부담 vs 강제력의 trade-off.

### 8.3 시나리오 C — 첫 가드 켜기

기본 `compose.yaml` 에 가드레일 정책이 이미 깔려 있다. 임계값만 조정 가능:

```yaml
guard:
  policies:
    cognitive_guard:
      per_call:    {max_diff_lines: 200, max_new_files: 3}
      per_session: {max_changed_files: 10, max_diff_lines: 1000}
      on_breach: ask_human
    loop_detection:
      consecutive_same_path: 3
      on_loop: self_correct
```

- `per_call.max_diff_lines: 200` — 한 번에 200줄 넘는 변경 시도 차단
- `per_session.max_diff_lines: 1000` — 세션 전체 누적 1000줄 넘으면 차단
- `consecutive_same_path: 3` — 같은 파일 연속 3번 수정 시 차단

처음엔 기본값으로 시작하고, *어떤 작업이 자꾸 막히면* 임계값을 늘리는 식으로 점진 조정. 깊은 튜닝은 [고급](03-고급.md).

### 8.4 시나리오 D — 결과 보기

```bash
cat .harness/runtime/AGENTS.resolved.md                              # LLM prefix 본문
cat .harness/runtime/sessions/<session-id>/decisions.jsonl           # hook 결정 로그
cat .harness/runtime/traces/<session-id>.jsonl                       # 도구 호출 trace
```

`<session-id>` 는 가장 최근 세션 폴더 이름. `ls .harness/runtime/sessions/` 로 확인.

`decisions.jsonl` 의 한 줄 예:
```json
{"hook":"pre_tool_use","role":"cognitive_guard","decision":"self_correct","reason":"per_call.max_diff_lines 200 초과 (실제 312)"}
```

이 로그가 *"내 가드레일이 실제로 무엇을 막았는가"* 의 1차 자료.

## 3부: 꼭 알아야 하는 디테일

여기까지로 시스템을 *돌릴 수 있다*. 3부는 운영하며 마주치는 핵심 개념을 짧게 정리. 깊은 튜닝은 [중급](02-중급.md)·[고급](03-고급.md).

## 9. 가드레일 — 켜고 끄기

가드레일은 *행동 자체에 거는 한계*. 3가지가 기본 제공된다.

### 9.1 Cognitive Guard

한 번에 너무 큰 변경을 차단. `compose.guard.policies.cognitive_guard` 에서 임계값 조정.

```yaml
cognitive_guard:
  per_call:    {max_diff_lines: 200, max_new_files: 3}
  per_session: {max_changed_files: 10, max_diff_lines: 1000}
  on_breach: ask_human
```

세션 누적은 `runtime/sessions/<id>/cognitive-guard.json` 에 기록된다.

### 9.2 Loop Detection

같은 path 를 의미 없이 반복 수정하는 패턴 (원인을 못 찾고 증상만 만지는 경우) 을 잡는다.

```yaml
loop_detection:
  consecutive_same_path: 3
  on_loop: self_correct       # | hard_stop
```

### 9.3 Stop Validation

응답 *종료 직전* 의 마지막 가드. 테스트·타입체크 등을 강제 실행해 통과 못 하면 응답을 못 끝내게 한다.

```yaml
stop_validation:
  enabled: false              # 기본 꺼짐 — 정말 강제하고 싶을 때 켜기
  on_fail: warn               # warn | block
  checks:
    - {command: "pytest -x"}
    - {command: "tsc --noEmit"}
```

매 응답마다 실행되므로 **빠른 check 만 두는 게 현실적**. 무거운 검증은 CI 에.

### 9.4 Bypass Marker — 진짜 큰 변경

리팩토링·마이그레이션처럼 의도적 큰 변경이 필요할 때, prompt 에 마커를 넣으면 한 번 통과:

```
@harness allow-large

이 큰 마이그레이션 적용해줘 ...
```

세션 동안 한 번만 cognitive guard 를 skip 한다.

> **튜닝 깊이는 [고급](03-고급.md)** — *"임계값을 어디까지 조이고 풀지"*, *"프로젝트 단계별 분기"*, *"데이터 기반 결정"* 등.

## 10. Hook 시스템

7개 hook 이 있고, 각각이 provider 의 어떤 이벤트에 응답한다.

| Hook id | 이벤트 | 주요 역할 |
|---|---|---|
| `session_start` | 세션 시작 | AGENTS.md 주입 / status 초기화 |
| `pre_tool_use` | 도구 호출 직전 | 가드 (required / cognitive / loop / context) |
| `post_tool_use` | 도구 호출 후 | trace·metric 갱신 |
| `post_tool_use_failure` | 도구 실패 시 | 실패 trace / eval verdict |
| `post_tool_batch` | 도구 묶음 종료 후 | metric 집계 |
| `permission_request` | 권한 요청 | 허용/거부 결정 |
| `stop` | 응답 종료 직전 | stop_validation |

각 hook 의 `handler.sh` 는 stdin 으로 envelope 을 받고, stdout 으로 JSON 결정을 응답한다:

| 응답 | 의미 |
|---|---|
| `{"decision":"allow"}` | 통과 |
| `{"decision":"self_correct","reason":"..."}` | 차단 + LLM 에 reason 전달, 재시도 |
| `{"decision":"hard_stop","reason":"..."}` | 즉시 정지 — 사용자 개입 |
| `{"decision":"block","reason":"..."}` (stop 한정) | 응답 종료 차단, 재작업 유도 |

한 hook artifact 가 manifest 에 **여러 role** 을 선언하고, compose 에서 어느 도메인 / 어느 role 로 활성화할지 선택한다 (1부 4장의 N:N 매핑).

## 11. Persona — 범위 제한

*"이 에이전트는 무엇을 하는 누구인가"* 를 미리 정해두는 것. **별도 메커니즘이 아니라 instructions artifact 한 개**.

```
<my-project>/.harness/know-how/instructions/backend_persona/
├── manifest.yaml
└── PERSONA.md
```

`PERSONA.md`:
```markdown
## Persona

당신은 이 프로젝트의 **백엔드 개발자** 입니다.
- 책임 영역: API 서버, 데이터베이스, 도메인 로직
- 다루지 않는 영역: 프론트엔드 UI, 디자인, 마케팅 카피
```

compose 에 추가:
```yaml
cognition:
  instructions:
    - agents_md
    - backend_persona
```

**3 요소만 있으면 충분:** 역할 / 책임 영역 / **다루지 않는 영역**. *다루지 않는 영역* 이 안전 측면의 핵심 — 명시 안 하면 LLM 이 "도와준다" 며 의도 외 영역까지 손댐.

(여러 persona 를 두고 작업별로 라우팅하는 multi-persona orchestration 은 [중급](02-중급.md).)

## 12. know-how — 자기 자산 추가

`know-how/` 는 standard 와 **같은 7 폴더 구조** 를 mirror 한다. 어느 메커니즘이든 자기 artifact 를 둘 수 있다.

```
<my-project>/.harness/know-how/
├── instructions/<id>/manifest.yaml + entry
├── hooks/<id>/manifest.yaml + handler.sh
├── tools/<id>/...
├── workflows/<id>/...
├── traces/<id>/...
└── evals/<id>/...
```

**기본 규칙 3개:**

1. **같은 패턴** — 어디든 `<id>/manifest.yaml + entry`. standard 와 동일.
2. **id 충돌 시 에러** — 같은 id 가 standard 와 know-how 양쪽에 있으면 `harness validate` 가 에러로 잡는다. override 하고 싶으면 **다른 id** 로 새 artifact 를 만들고 compose 에서 그 id 를 활성화.
3. **검증되면 standard 로 승격** — 충분히 일반적이고 검증된 자산은 standard 로 promote 가능. 자세한 흐름은 [중급](02-중급.md).

**id 명명 규칙**

- `snake_case` (`backend_persona` ✓, `BackendPersona` ✗, `backend-persona` ✗)
- 시스템 전체에서 **unique** (standard + know-how 통틀어)
- 의미 있는 단어 — `project_readme` ✓, `r1` ✗, `tmp` ✗
- 한글 letter 도 가능 (Unicode letter)

## 13. 문제 해결 — 세 명령 + 로그

뭔가 안 돌아갈 때 순서:

```bash
harness doctor       # 환경 진단 — 어디가 깨졌는지
harness validate     # compose.yaml + manifests + roles 일관성 검증
harness list         # 어떤 자산이 보이는지 (글로벌 + 프로젝트)
```

여전히 안 보이면 runtime 데이터:

```bash
ls .harness/runtime/sessions/                                          # 최근 세션 폴더들
```

`runtime/sessions/<session-id>/` 안에 있는 주요 파일들:

| 파일 | 무엇이 들어있나 |
|---|---|
| `meta.json` | 세션 시작 시각, provider, transcript path 등 메타 |
| `decisions.jsonl` | hook 결정 로그 (allow / self_correct / hard_stop + 이유) — 가장 자주 보게 됨 |
| `prompts.jsonl` | user_prompt_submit 이 기록한 사용자 입력 |
| `required-status.json` | Required Context 읽음 추적 |
| `cognitive-guard.json` | 세션 누적 변경 파일·라인 (가드 카운터) |
| `timing.json` | 도구 시작·종료 시각 (post_tool_use diff 용) |

그리고 도구 호출 trace 는 별도 위치:
```bash
cat .harness/runtime/traces/<session-id>.jsonl                        # 도구 trace raw
```

`decisions.jsonl` 이 *"내 정책이 실제로 무엇을 막았는가"* 의 1차 자료. 차단이 너무 많으면 임계값 조정, 정책이 작동 안 하는 것 같으면 `harness doctor` 부터.

## 4부: 다음 단계

## 14. 입문을 마쳤다면

여기까지 따라왔다면:

- 글로벌 + 프로젝트 단위로 시스템을 깔고
- `compose.yaml` 한 파일로 정책을 정하고
- 가드레일 / persona / know-how 자산까지 다룰 수 있다

다음 단계는 *확장* 과 *trade-off 조절*.

### 14.1 더 깊이, 더 넓게 → [중급](02-중급.md)

- **위임·병렬** — subagent / worktree 로 한 에이전트의 한계를 넘는다
- **맥락 (연속성)** — 세션 횡단 컨텍스트, 컨텍스트 관리
- **multi-persona / multi-agent** — 여러 역할·여러 모델 조합
- **workflows 활용** — ralph 무인 루프와 자가 구동 패턴
- **측정** — traces / evals / improve 로 시스템 자체를 분석

### 14.2 Trade-off 마스터 → [고급](03-고급.md)

- 안전 ↔ 성능 의 trade-off 결정 frame
- 데이터 기반 결정 (직관 대신 측정)
- 조직 단위 운영 (정책 통일 vs 분기)
- 운영 사례
- **자가 진화 — 시스템이 스스로 진화하는 도전 과제** (아직 정립된 답이 없는 영역)

### 14.3 한 줄로

> *"내 인지 한계를 넘는 일은 LLM 에게도 시키지 않는다."*

이 한 줄이 시스템의 본질. Hook 으로 의도 외 행동을 차단하고, 가드레일로 인지 한계를 보호하고, persona 로 범위를 좁힌다 — 사람과 LLM 이 같은 속도로 갈 수 있게.

이 흐름을 자신의 프로젝트에서 한 번 직접 운영해본 사람만이 다음 단계의 *확장* 과 *trade-off* 에서 의미 있는 결정을 할 수 있다. 천천히, 한 단계씩.
